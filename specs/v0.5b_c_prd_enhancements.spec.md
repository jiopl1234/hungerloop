## 1. `hungerloop report` output format

### 1.1 Gap

`§1.1` lists `hungerloop report` in v0.5b.0 scope; nothing in the PRD specifies what it emits. The same task summary today is hand-formatted by `cli/status_format.py` for `hungerloop status`. Without a spec, every team that consumes task output will write a different parser.

### 1.2 Recommended design

- Default output: **JSON to stdout**, machine-readable, pipeable into `jq`. One object per invocation. Always includes `schema_version` for forward compat.
- `--format markdown`: human-readable summary, suitable for PR comments / chat.
- No YAML form; YAML is the input language (configs), JSON is the output language (state).
- Stable schema (v1):

```json
{
  "schema_version": "1",
  "task_id": "demo-1",
  "goal": "Create a small report and validate it.",
  "stop": {
    "reason": "done",
    "goal_status": "completed",
    "recommendation": ""
  },
  "ledger": {
    "items_total": 3,
    "items_satisfied": 2,
    "items_blocked": 1,
    "items_open": 0
  },
  "usage": {
    "tokens": 1842,
    "cost_usd": 0.0231,
    "llm_calls": 4,
    "tool_calls": 7
  },
  "loops": {
    "total": 5,
    "committed": 2,
    "rejected": 3
  },
  "best_state_id": "STATE-demo-1-2",
  "accepted_check_keys": ["H-001:0", "H-001:1"],
  "last_loop": {
    "loop_id": 5,
    "phase": "EXPLOIT",
    "delta_summary": "committed (newly_passed: H-001:1)"
  }
}
```

`hungerloop status` keeps its current human-only output; `hungerloop report` is the contract for tools.

### 1.3 EARS requirements

- **U-RPT-01** When `hungerloop report <task_id>` runs without `--format`, the CLI shall emit JSON to stdout.
- **E-RPT-02** When `--format markdown`, the CLI shall emit a human-readable summary; no JSON.
- **U-RPT-03** Every JSON output shall include `schema_version: "1"` at the root.
- **E-RPT-04** When the task does not exist, the CLI shall exit code 1 and print `Task not found: <task_id>` to stderr (no JSON to stdout).
- **E-RPT-05** When the task has no StopReport (still running or never run), the `stop` object shall contain `reason: null` and the CLI shall exit 0.
- **U-RPT-06** Field additions to schema v1 shall be backward-compatible (added keys only). Removals or type changes require `schema_version: "2"`.

### 1.4 Acceptance criteria

```
Given a completed demo task with stop_reason=DONE,
When `hungerloop report demo-1` is invoked,
Then stdout shall be a single JSON object with stop.reason="done"
  and exit code 0.

Given a task that does not exist,
When `hungerloop report missing-1` is invoked,
Then stdout shall be empty,
  stderr shall contain "Task not found: missing-1",
  and exit code shall be 1.

Given a task that is currently running (no StopReport yet),
When `hungerloop report task-x --format markdown` is invoked,
Then stdout shall contain a "Status: running" line
  and exit code shall be 0.
```

### 1.5 Implementation hooks

- New module `cli/report_cmd.py`.
- New formatter `cli/report_format.py` (mirrors `status_format.py` but JSON-first).
- Tests: `tests/unit/test_cli_report.py` covering empty/running/done/error states + JSON schema validation.
- PRD insertion: §18.3.

## 2. SQLite schema migration strategy

### 2.1 Gap

`§5.1` sets `PRAGMA user_version = 1` (the line is implicit; the SQL has no `PRAGMA user_version`). Once SQLite ships, every additive table or column becomes a breaking change without a migration policy. v0.6 needs LearningWorker tables, ResearchWorker tables, MemoryPromotion fields — those land into a frozen schema unless we set the rules now.

### 2.2 Recommended design

- **Forward-only migrations**. No down-migrations. To revert, restore from backup.
- Migration files: `src/hungerloop/repository/migrations/v{N}__{slug}.sql` (e.g., `v2__add_memory_promotion_state.sql`). Each file is one transaction.
- `SQLiteRepository.__init__`:
  1. Open the DB.
  2. Read `PRAGMA user_version`. Call this `current`.
  3. If `current > LATEST`: refuse to open. `SchemaTooNewError("DB at v{current}, code at v{LATEST}; downgrade not supported")`.
  4. If `current < LATEST`: write a sibling backup at `blackboard.sqlite.bak.v{current}.{ts}`, then apply each migration in order, each in its own `BEGIN IMMEDIATE`.
  5. After successful migration, update `PRAGMA user_version = N`.
  6. Acquire task lock (separate transaction).
- Migrations only run on commands that take the write lock (`run`, `new`, `hunger refill/unblock/freeze/resume`, `repair-state --fix`). Read-only commands (`status`, `report`, `trace`, `repair-state --check`) refuse to open a DB whose `user_version < LATEST` to avoid silent half-migrations across processes.
- v0.5b.0 ships with `LATEST = 1` and migrations dir empty. The first real migration lands when v0.5c.0 adds memory tables.

### 2.3 EARS requirements

- **U-MIG-01** Every SQLite open operation shall verify `user_version` against `LATEST` before any table read.
- **E-MIG-02** When `user_version < LATEST` on a write-capable command, the system shall apply pending migrations inside a single transaction per migration file, in version order.
- **E-MIG-03** Before migrating, the system shall write a sibling backup `<db>.bak.v{old_version}.{iso8601_ts}`.
- **E-MIG-04** When `user_version < LATEST` on a read-only command, the system shall exit code 4 with `Database needs migration; run 'hungerloop run' or '--migrate' once`.
- **E-MIG-05** When `user_version > LATEST`, the system shall raise `SchemaTooNewError` and refuse to open.
- **U-MIG-06** Migrations shall be forward-only; no down-migration files exist.
- **U-MIG-07** Each migration file shall be idempotent under retry (tested by re-running on a fresh copy of the post-migration DB).

### 2.4 Acceptance criteria

```
Given a v1 DB and code at LATEST=2,
When a write command opens the DB,
Then a backup file matching pattern *.bak.v1.* exists,
  user_version = 2,
  and the new schema is queryable.

Given a v3 DB and code at LATEST=2,
When any command opens the DB,
Then the command exits code 5 with "downgrade not supported"
  and the DB is unmodified.

Given a v1 DB and code at LATEST=2,
When `hungerloop status` (read-only) opens the DB,
Then it exits code 4 with a "Database needs migration" message
  and user_version is still 1.
```

### 2.5 Error table

| Error | Detection | Action |
|---|---|---|
| `SchemaTooNewError` | `user_version > LATEST` | Refuse open; print remediation |
| Migration SQL fails mid-transaction | `sqlite3.Error` inside `BEGIN IMMEDIATE` | Roll back the migration; preserve backup; raise |
| Backup write fails (disk full) | `OSError` before migration | Refuse to migrate; raise; user gets a clear error before any schema mutation |
| Migration file referenced by version pointer doesn't exist | Filesystem check at startup | Refuse to open; "code/repo mismatch" error |

### 2.6 Implementation hooks

- `repository/migrations/v1__initial.sql` (the current `sqlite_schema.sql`, renamed).
- `repository/sqlite_migrator.py` — version detection, backup, apply.
- Tests: `tests/unit/test_sqlite_migrator.py` covering happy path, downgrade refusal, mid-migration failure rollback, read-only refusal.
- PRD insertion: §5.5.

## 3. `repair-state` command behavior

### 3.1 Gap

§16.3 and §22.3 reference `hungerloop repair-state <task_id> --check / --fix` but never specify what it checks or what it dares to fix. v0.5b.0 needs at least `--check` (per §22.3 manifest verification). `--fix` left vague is dangerous — "auto-repair" tools that overstep cause real damage.

### 3.2 Recommended design

**Three categories of divergence**, each with explicit policy:

| Divergence | `--check` reports | `--fix` does |
|---|---|---|
| **D1**: Manifest exists, file present, hashes match | OK | nothing |
| **D2**: Manifest exists, file present, hash mismatch | **CORRUPTION** | refuse — exit 2 with "manual intervention required" |
| **D3**: Manifest exists, file missing | **CORRUPTION** | refuse — exit 2 |
| **D4**: File present, no manifest entry | warn | rewrite manifest from filesystem (filesystem is truth) |
| **D5**: Orphan candidate workspace (no LoopTrace, no candidate row) | warn | move to `rejected/loop_NNN/` |
| **D6**: Stale task lock (`now - locked_at > stale_threshold`) | warn | refuse — `--fix` does not steal locks; `--steal-lock` is the explicit affordance |
| **D7**: `accepted_checks` row references missing `validation_id` | warn | refuse — pure SQLite repair, needs separate tooling |

**Core rule**: `--fix` is allowed iff the repair direction is "filesystem is truth, SQLite is auxiliary index." Never overwrite files to match SQLite. Never delete files. Never modify hashes.

`--check` exit codes:
- 0: clean
- 1: warnings only (D4, D5, D6)
- 2: corruption (D2, D3)

`--fix` exit codes:
- 0: all repairable divergences fixed
- 2: corruption present, manual intervention needed
- 3: nothing to fix

### 3.3 EARS requirements

- **U-RPR-01** `repair-state --check` shall be read-only across SQLite and the filesystem.
- **E-RPR-02** When manifest hash mismatch is detected (D2), `--fix` shall refuse and exit code 2.
- **E-RPR-03** When manifest is missing for a present file (D4), `--fix` shall regenerate the manifest from the filesystem.
- **E-RPR-04** When an orphan candidate workspace is detected (D5), `--fix` shall move it to `rejected/loop_NNN/`.
- **U-RPR-05** `--fix` shall never delete files in `best/` or `candidates/`.
- **U-RPR-06** `--fix` shall never overwrite an existing file in `best/`.
- **E-RPR-07** When a stale task lock is detected (D6), `--fix` shall refuse and instruct the user to use `--steal-lock` (see §4 below).
- **U-RPR-08** Every `--fix` action shall append a `repair_state_action` event with the divergence type, files affected, and outcome.

### 3.4 Acceptance criteria

```
Given a task with a present file and matching manifest hash (D1),
When `repair-state --check` runs,
Then it exits 0 with "clean".

Given a task where best/files/report.md exists but manifest is missing (D4),
When `repair-state --fix` runs,
Then the manifest is rewritten from filesystem hashes,
  a repair_state_action event is appended,
  and exit code is 0.

Given a task whose manifest hash for report.md does not match the file (D2),
When `repair-state --fix` runs,
Then no files are modified,
  and exit code is 2 with "corruption: manual intervention required".

Given an orphan candidate workspace candidates/loop_007 with no LoopTrace,
When `repair-state --fix` runs,
Then loop_007 is moved to rejected/loop_007,
  best/ is untouched,
  and exit code is 0.
```

### 3.5 Implementation hooks

- `cli/repair_state_cmd.py`.
- `services/repair_state.py` — divergence detection (read-only) and idempotent repair.
- Tests: `tests/unit/test_repair_state.py` covering D1-D7 with synthetic states.
- PRD: expand §16.3.

## 4. Task lock fault recovery (§5.1 hardening)

### 4.1 Gap

§5.1 specifies `tasks.lock_owner / locked_at` and "only one runner may own a lock at a time." Missing: stale-lock detection, crash recovery, force-steal, lock-release ordering on clean shutdown.

### 4.2 Recommended design

- Lock owner string: `"{hostname}:{pid}:{uuid4_8}"`. Recorded fully so a human can identify "which terminal."
- Stale threshold: 30 minutes (configurable via env `HUNGERLOOP_LOCK_STALE_SEC`).
- On `hungerloop run` startup:
  1. `BEGIN IMMEDIATE`.
  2. Read `lock_owner`, `locked_at`.
  3. If `lock_owner is null`: claim it, commit, proceed.
  4. If held by *self* (same hostname:pid): proceed — re-entrant.
  5. If held and `now - locked_at < stale_threshold`: exit 3 with the current owner.
  6. If held and stale: exit 6 with `--steal-lock` instructions.
- On clean shutdown (StopReport persisted): release the lock in the *same transaction* that writes the StopReport (atomic: stop_report saved AND lock released, or neither).
- On crash: lock stays held. Recovery requires `--steal-lock`.
- `hungerloop run --steal-lock <task_id>`: explicit force; appends a `lock_stolen` event with `prev_owner`, `new_owner`, `prev_locked_at`. Then proceeds normally.

### 4.3 EARS requirements

- **E-LOK-01** When `hungerloop run` finds a lock held by another live process (`now - locked_at < HUNGERLOOP_LOCK_STALE_SEC`), it shall exit code 3 with `Lock held by <owner> since <ts>`.
- **E-LOK-02** When the lock is stale, `run` shall exit code 6 with `--steal-lock` instructions; it shall not auto-steal.
- **E-LOK-03** When `--steal-lock` is passed, the system shall replace the owner inside `BEGIN IMMEDIATE` and emit a `lock_stolen` event.
- **U-LOK-04** Lock release on clean shutdown shall be in the same transaction that persists the StopReport.
- **U-LOK-05** Re-entrant runs (same hostname:pid) shall succeed without `--steal-lock`.
- **E-LOK-06** When `repair-state --check` detects a stale lock, it shall report it as D6 and not steal.

### 4.4 Acceptance criteria

```
Given a task with no lock owner,
When `hungerloop run task-1` starts,
Then lock_owner is set to {hostname}:{pid}:{uuid},
  locked_at = now,
  and the run proceeds.

Given a task with lock_owner held by another live PID, locked_at = 5 min ago,
When `hungerloop run task-1` starts,
Then it exits code 3
  with the current owner string in stderr
  and no events are appended.

Given a task with lock locked_at = 60 min ago (stale),
When `hungerloop run task-1` starts (no --steal-lock),
Then it exits code 6
  with --steal-lock instructions.

Given the same stale lock,
When `hungerloop run task-1 --steal-lock` runs,
Then a lock_stolen event is appended,
  lock_owner becomes the new caller,
  and the run proceeds.

Given an orchestrator that completes with stop_reason=DONE,
When the StopReport is persisted,
Then the same transaction sets lock_owner = NULL.
```

### 4.5 Error table

| Code | Meaning | Suggested action |
|---|---|---|
| 3 | Lock held by another live process | Wait, or check that process |
| 6 | Stale lock | `--steal-lock` after verifying previous owner is dead |
| (no special) | Re-entrant from same PID | Proceeds |

### 4.6 Implementation hooks

- `repository/sqlite_repo.py::acquire_task_lock / release_task_lock / steal_task_lock` (already in protocol §4.1, behavior here).
- `cli/run_cmd.py` adds `--steal-lock`.
- Tests: lock contention, stale detection, steal, atomic-release.
- PRD insertion: §5.1.1.

## 5. MemoryCandidate promotion lifecycle (forward shape)

### 5.1 Gap

§19.1 says v0.5c only proposes; promotion is "deferred to v0.6." But the *schema* of `MemoryCandidate` is being frozen at v0.5c — and v0.6 will need fields the current model doesn't have. Setting them now costs nothing; adding them later is a SQLite migration.

### 5.2 Recommended design

Add four fields **to the v0.5c MemoryCandidate model**, even though only `state="proposed"` is written in v0.5c:

```python
class MemoryCandidate(BaseModel):
    candidate_id: str
    task_id: str
    loop_id: int
    summary: str
    evidence_ids: list[str]
    predicates: dict[str, bool]   # action_verified, reusable, non_volatile, traceable

    # NEW for forward compat
    state: Literal["proposed", "approved", "rejected", "expired", "superseded"] = "proposed"
    decision_loop_id: int | None = None
    decided_by: Literal["human", "auto", None] = None
    decision_rationale: str = ""
    replaces_candidate_id: str | None = None
```

v0.5c rules:
- All emitted candidates have `state="proposed"`.
- `decision_*` and `replaces_*` are always null/empty.
- `MemoryManager` does not write any other state.
- `hungerloop memory list` filters by state when `--state` is passed (default = all).

v0.6 adds:
- Promotion CLI: `hungerloop memory approve <candidate_id>` / `reject` / `supersede`.
- Auto-promotion job that flips `state="approved"` when all predicates remain true after `min_committed_refs` loops.
- A `superseded` candidate's `replaces_candidate_id` points back at the predecessor — chain query for memory genealogy.

### 5.3 EARS requirements

- **U-MEM-01** `MemoryCandidate.state` shall be one of `proposed/approved/rejected/expired/superseded`.
- **U-MEM-02** v0.5c shall only emit candidates with `state="proposed"`; all decision fields null.
- **E-MEM-03** When v0.6 promotion is implemented, it shall set `state` and `decision_loop_id` and `decided_by` in one repository write.
- **U-MEM-04** A `superseded` candidate shall reference its successor via the new candidate's `replaces_candidate_id`, not via a backward pointer (one-way chain).
- **E-MEM-05** `hungerloop memory list --state proposed` shall return only candidates with `state="proposed"`.

### 5.4 Acceptance criteria

```
Given a v0.5c run that emits one MemoryCandidate,
When the row is read back,
Then state == "proposed",
  decision_loop_id is null,
  decided_by is null,
  and decision_rationale is "".

Given two candidates A and B where B.replaces_candidate_id == A.candidate_id,
When the genealogy is queried via the new helper,
Then the result is [B, A] in successor-first order.
```

### 5.5 Implementation hooks

- Update `models/memory.py` with the four new fields.
- Update `services/memory_manager.py` to set `state="proposed"` (already implicit, make explicit).
- Update `repository/sqlite_schema.sql` `memory_candidates` table to include the new columns from day one.
- Tests: schema round-trip + `--state` filter.
- PRD: expand §19.1.

## 6. Cost estimate vs actual reconciliation

### 6.1 Gap

`PricingTable` estimates token cost pre-call. `OpenAIModelClient` records actual usage post-call. PRD doesn't specify what happens when they diverge — common cases: prompt caching changes effective tokens; vision tokens are different; completion length surprise.

### 6.2 Recommended design

- Pre-call: BudgetGuard checks against the *estimate*. This is a safety floor — keep it.
- Post-call: `OpenAIModelClient` already calls `cost_guard.record_llm_usage(actual_tokens, actual_cost)`. Add: emit a `cost_reconciliation` event when `|actual - estimate| / estimate > 0.20` (configurable via `HUNGERLOOP_COST_DELTA_THRESHOLD`).
- Event payload:
  ```json
  {
    "task_id": "...", "loop_id": ..., "model": "gpt-4o-mini",
    "estimated_tokens": 1200, "actual_tokens": 1850,
    "estimated_cost_usd": 0.0024, "actual_cost_usd": 0.0037,
    "delta_ratio": 0.54
  }
  ```
- BudgetGuard state is **not retroactively rewritten** — pre-call estimates were honest at the time. Reconciliation is observability, not enforcement.
- The `unknown_model_pricing` event (already in PRD) is a sibling concept: emit it when PricingTable has no entry; reconciliation cannot run without an estimate.

### 6.3 EARS requirements

- **E-CRC-01** When `|actual_tokens - estimated_tokens| / estimated_tokens > 0.20`, the system shall append a `cost_reconciliation` event.
- **U-CRC-02** `cost_reconciliation` events shall not retroactively modify BudgetGuard or CostGuard state.
- **E-CRC-03** When PricingTable returns no estimate for a model, no `cost_reconciliation` event shall fire (the prior `unknown_model_pricing` event covers this).
- **U-CRC-04** The delta threshold shall be configurable via `HUNGERLOOP_COST_DELTA_THRESHOLD` (default 0.20).

### 6.4 Acceptance criteria

```
Given a model call with estimate=1000 tokens and actual=1500 tokens,
When the post-call reconciliation runs,
Then a cost_reconciliation event is appended with delta_ratio=0.5
  and BudgetGuard state reflects only actual=1500.

Given a model call with estimate=1000 and actual=1100,
When the post-call reconciliation runs,
Then no cost_reconciliation event is appended (within 20% threshold).
```

### 6.5 Implementation hooks

- `services/openai_model_client.py` post-call block.
- Tests: `tests/unit/test_cost_reconciliation.py`.
- PRD insertion: §8.7.1.

## 7. Observability event vocabulary

### 7.1 Gap

§22 covers logging, status file, manifest, redaction. Missing: a stable canonical list of `event_type` strings. Without one, ops dashboards built later have to reverse-engineer them from grep'ing the codebase, and event names drift.

### 7.2 Recommended design

Don't add a metrics framework in v0.5b. Instead:

1. **Freeze the event vocabulary** as a documented enum in `models/enums.py` (or a separate `events.py`):

```python
class EventType(str, Enum):
    # Loop lifecycle
    LOOP_STARTED = "loop_started"
    LOOP_COMMITTED = "loop_committed"
    LOOP_REJECTED = "loop_rejected"

    # Hunger
    HUNGER_RESUMED = "hunger_resumed"
    HUNGER_FROZEN = "hunger_frozen"
    HUNGER_REFILLED = "hunger_refilled"

    # Stops
    SAFETY_STOP = "safety_stop"
    HUMAN_REQUIRED = "human_required"

    # Cost / pricing
    COST_RECONCILIATION = "cost_reconciliation"
    UNKNOWN_MODEL_PRICING = "unknown_model_pricing"

    # Locks / repair
    LOCK_STOLEN = "lock_stolen"
    REPAIR_STATE_ACTION = "repair_state_action"

    # Memory / skill
    MEMORY_CANDIDATE_EMITTED = "memory_candidate_emitted"
    SKILL_CARD_EMITTED = "skill_card_emitted"
```

2. **Document the contract** in §22.8: every event has `task_id`, `loop_id` (nullable), `event_type`, `payload`, `created_at`. Adding new event types is additive only; renaming requires schema bump.

3. **Provide `hungerloop trace export <task_id> [--format jsonl]`** for streaming events to external tools. JSONL is the ops contract. v0.6+ can layer Prometheus/OpenTelemetry adapters on top of this.

### 7.3 EARS requirements

- **U-OBS-01** Every event written via `append_event` shall use an `EventType` enum value, not a literal string.
- **U-OBS-02** Adding new `EventType` values shall be additive; renaming or removing requires a schema migration.
- **E-OBS-03** When `hungerloop trace export <task_id>` runs without `--format`, it shall emit JSONL to stdout, one event per line.
- **U-OBS-04** The system shall not run an embedded metrics server in v0.5b.

### 7.4 Acceptance criteria

```
Given a task with 3 loops and one cost_reconciliation event,
When `hungerloop trace export task-x` runs,
Then stdout contains 1 line per event in chronological order
  and each line is valid JSON
  and each line's event_type is in EventType.

Given a developer attempts append_event("typo_event_name", ...),
When mypy --strict runs,
Then it fails (event_type parameter is typed as EventType).
```

### 7.5 Implementation hooks

- `models/events.py` (new) with `EventType` enum.
- `repository/protocol.py::append_event` signature: `event_type: EventType` (not `str`).
- `cli/trace_cmd.py` adds `export` subcommand.
- Tests: enum coverage; JSONL round-trip.
- PRD insertion: §22.8.

## 8. DummyModelClient long-term contract

### 8.1 Gap

DummyModelClient is treated as a v0.5a-only test fixture. Once OpenAIModelClient lands in v0.5b.1, there's no statement on whether Dummy stays. In practice: tests, demos, CI smoke runs, and offline development all need it. Undocumented = drift risk.

### 8.2 Recommended design

- **Keep DummyModelClient as a sanctioned offline mode** beyond v0.5b. Roles: tests, demos, deterministic CI.
- **Add `provider: dummy` to ModelConfig** as a first-class option (not an `if testing` branch). Loader does not require `api_key_env` for dummy.
- **Freeze the scripted-action API** at v0.5b. Schema:
  ```python
  DummyModelClient.with_actions([
      {"tool_name": "write_file", "args": {"path": "report.md", "content": "ok"}},
      {"tool_name": "run_shell", "args": {"argv": ["pytest", "-x"]}},
  ])
  ```
  Additions allowed (new `tool_name` or `args` keys). Removals or type changes require a major version bump on the action schema.
- **Document the production guard**: `cli/orchestrator_factory.py` shall warn (not refuse) when `provider == "dummy"` and `--allow-dummy` is not passed; tests bypass via `CliContext(model_client=...)` injection. Production users get a friendly nudge.

### 8.3 EARS requirements

- **U-DMY-01** `DummyModelClient` shall be retained as a sanctioned offline mode in v0.5b and beyond.
- **E-DMY-02** When `ModelConfig.provider == "dummy"`, the loader shall not require `api_key_env`.
- **E-DMY-03** When `hungerloop run` is invoked with `provider=dummy` and without `--allow-dummy`, the CLI shall print a warning to stderr but proceed.
- **U-DMY-04** The `with_actions([...])` schema shall be additive-compatible across v0.5b–v0.6; field removals require a major bump.
- **U-DMY-05** Tests injecting a DummyModelClient via `CliContext(model_client=...)` shall not trigger the production warning (warning lives in the YAML loader path only).

### 8.4 Acceptance criteria

```
Given a model_config.yaml with provider: dummy and no api_key_env,
When ModelConfigLoader loads it,
Then it succeeds without error.

Given a `hungerloop run task-1 --model-config dummy.yaml` invocation,
When provider is dummy and --allow-dummy is absent,
Then stderr contains "Warning: using DummyModelClient"
  and the run proceeds.

Given a unit test injecting DummyModelClient via CliContext,
When `runner.invoke(cli, ["run", "t1"], obj=ctx)` is called,
Then no warning is printed.
```

- `services/model_config.py` accepts `provider: dummy`.
- `cli/run_cmd.py` adds `--allow-dummy` and the warning.
- `services/model_client.py` — add a frozen comment block on `with_actions` action schema as the contract anchor.
- Tests: loader accepts dummy; warning printed on YAML path; not printed on injection path.

## 11. Decisions (locked 2026-05-04)

1. **`report` markdown vs `status` markdown**: **distinct-purpose**. `hungerloop report` is JSON-first; `--format markdown` is its own template aimed at PR comments / chat. `hungerloop status` keeps its existing human format independently. Sharing byte-for-byte would lock both formats together forever and force every status tweak through the JSON-schema review process.
2. **Migration backup retention**: keep the latest backup plus the **2 prior versions**; prune older to `<workspace>/.archive/`. Backups are a few MB each; corruption recovery without one is operator-grade pain.
3. **Stale-lock threshold**: 30-minute default exposed via env `HUNGERLOOP_LOCK_STALE_SEC` and per-invocation override via `hungerloop run --lock-stale-sec N`. Not a `HungerPolicy` field — keeps the policy model focused on hunger, not lock plumbing.
4. **MemoryCandidate expiry**: time-based, default **90 days** from `created_at`. The auto-expiry job is v0.6 work; v0.5c only documents the field semantics so v0.6 doesn't need a schema migration to add `expires_at`.
5. **DummyModelClient policy**: **warning-only** on the YAML loader path; test injection via `CliContext(model_client=...)` is silent. `HUNGERLOOP_QUIET_DUMMY=1` suppresses the warning for CI. Hard refusal would force every offline demo and CI smoke test to thread `--allow-dummy` through wrappers; the friction outweighs the safety gain.

These decisions are reflected in the per-task implementation files under `specs/v0.5b_c_implementation/`.
