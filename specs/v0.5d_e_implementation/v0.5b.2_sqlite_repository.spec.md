# v0.5b.2 — SQLiteRepository Hard Gate

**Release:** v0.5b.2 (release-blocker for v0.5d.0)
**PRD:** `hungerloop_v0_5d_e_prd_revised.md` §3
**Status:** spec → ready to implement

---

## 1. Overview

### 1.1 What

Ship the on-disk persistence backend HungerLoop has deferred since
v0.5a. `SQLiteRepository` implements the full `RepositoryProtocol`
(48 methods today + the v0.5d/e observability additions), wires up
through the existing forward-only migrator, and replaces the v0.5a
"CLI cannot run without SQLiteRepository" error with a working
default backend.

### 1.2 Why

Every v0.5d/e acceptance criterion ("orchestrator events are written",
"trace exports persist across restarts", "memory candidates are
SQL-queryable") is unmeasurable without SQLite on disk. The PRD makes
v0.5b.2 a hard gate; nothing in §5 onwards can be tested without it.

### 1.3 User value

- **Operators:** the CLI works after `pip install -e .` without
  test-only context injection.
- **Tasks:** state survives process exit. `hungerloop run`, ctrl-c,
  `hungerloop run --resume` continues where the previous process
  stopped.
- **Reviewers:** the 14-table v1 + v2 schema that's been a design
  doc for two milestones now actually has a writer.

### 1.4 Non-goals

- v0.5d's **new** protocol methods (`list_events`, `list_candidates_for_task`,
  `list_successful_tool_call_evidence`, etc.). Those land in v0.5d.0
  alongside the orchestrator changes — see PRD §6.
- Migration v3/v4/v5 (those are v0.5d/v0.5e scope; v0.5b.2 stays at
  `LATEST_VERSION = 2`).
- Any LLMPlanner / 3×3 agent / web UI.
- Cross-task scheduler (one-task-per-process is the contract).

## 2. Functional requirements (EARS)

### 2.1 Repository implementation

**FR-1.** The system shall provide an `SQLiteRepository` class that
implements every method on the existing `RepositoryProtocol` (48
methods across 8 sections; full list at `protocol.py`).

**FR-2.** When `SQLiteRepository(db_path).open()` is called against
a path that does not exist, the system shall create the file, run the
forward-only migrator (`v1__initial.sql` then
`v2__memory_candidate_lifecycle.sql`), and set `PRAGMA user_version =
LATEST_VERSION`.

**FR-3.** When `SQLiteRepository(db_path).open()` is called against a
file with `user_version > LATEST_VERSION`, the system shall raise
`SchemaTooNewError` and refuse to open the database.

**FR-4.** When `SQLiteRepository(db_path).open()` is called against a
file with `user_version < LATEST_VERSION`, the system shall apply the
pending migrations transactionally (one `BEGIN IMMEDIATE` per file)
with sibling backup retained per the shipped migrator policy.

### 2.2 Connection lifecycle and concurrency

**FR-5.** The system shall enable WAL journal mode
(`PRAGMA journal_mode = WAL`) on every connection it opens.

**FR-6.** The system shall set `PRAGMA busy_timeout = 5000` on every
connection so concurrent readers do not fail with `database is
locked` under normal load.

**FR-7.** Where two processes attempt to acquire the task lock for the
same `task_id`, the system shall return `held_live` to the second
caller (per the shipped `acquire_task_lock` contract from b0-04).

**FR-8.** When a process holding a task lock crashes, the system shall
leave the lock row in place; the next caller observes
`now - locked_at >= stale_threshold_seconds` and resolves via the
shipped stale / steal logic.

### 2.3 Transaction semantics

**FR-9.** When `repo.transaction()` is entered, the system shall
issue `BEGIN IMMEDIATE`; when the context exits cleanly, the system
shall `COMMIT`; when the context exits with an exception, the system
shall `ROLLBACK` and propagate the exception.

**FR-10.** Where `CommitManager.apply` runs inside a `transaction()`,
the system shall ensure that either every write within the block
lands on disk or none do.

### 2.4 CLI default backend

**FR-11.** When `hungerloop` is invoked without an injected
`CliContext`, the system shall build a default context backed by
`SQLiteRepository` rooted at `${HUNGERLOOP_HOME:-~/.hungerloop}/blackboard.sqlite`.

**FR-12.** When the default `HUNGERLOOP_HOME` directory does not
exist, the system shall create it with mode `0700`.

**FR-13.** Where the user passes `--db <path>`, the system shall use
the supplied path instead of the default.

**FR-14.** When the resolved `blackboard.sqlite` path is on a
read-only filesystem and the invoked command is write-capable, the
system shall raise `click.ClickException` with text "Database is
read-only; cannot run write command" and exit code 4.

### 2.5 Restart-state parity

**FR-15.** When a process writes any of the following and exits
cleanly, the next process opening the same database shall observe
identical values:

```
tasks.task_id, status, last_stop_reason
best_states.state_id (most recent BestState)
accepted_checks (full set of (task_id, check_key) tuples)
hunger_clocks.loop_count, hunger, frozen
hunger_items.status, consecutive_failure_count (per item)
usage_snapshots.total_tokens, total_cost_usd, llm_calls, tool_calls
last loop_traces.loop_id and committed flag
last stop_reports row (stop_reason, goal_status, total_loops)
events log (no rows lost across restart)
```

**FR-16.** When a process holding a task lock exits cleanly, the
system shall release the lock so a subsequent `run` does not see
`held_live`.

### 2.6 Behavioural parity with InMemoryRepository

**FR-17.** Where a test-suite parametrizes over both `InMemoryRepository`
and `SQLiteRepository`, every protocol method shall produce
behaviourally equivalent results (identical return values for
read-after-write, identical error types for invalid inputs).

**FR-18.** When `SQLiteRepository.append_event(event_type, payload,
task_id, loop_id)` is called, the system shall persist the
`event_type.value` string (not the enum), matching the shipped
InMemory contract from b0-05.

**FR-19.** When `SQLiteRepository` reads back a stored
`MemoryCandidate`, the system shall return a model with all c0-01
lifecycle fields (`state`, `expires_at`, `decision_loop_id`,
`decided_by`, `decision_rationale`, `replaces_candidate_id`)
populated from their columns, not just from `payload_json`.

### 2.7 CLI no longer reads private repo state (deferred clean-up)

**FR-20.** v0.5b.2 may keep the existing `getattr(repo, "_events")`-
style private accesses in `report_format.py`, `trace_cmd.py`, and
`repair_state.py`. Removing them is v0.5d.0's job; v0.5b.2 only needs
to ensure those accesses still work against `SQLiteRepository` —
either by exposing the same private dicts or by adding the
corresponding protocol methods early.

## 3. Non-functional requirements

### 3.1 Performance

**NFR-1.** The system shall complete `hungerloop status <task_id>` and
`hungerloop report <task_id>` in under 200 ms median across 5 runs
against a fixture task with 100 loops + 100 evidence rows + 5
best-state promotions (matches the c1-01 perf budget).

**NFR-2.** The system shall complete `repo.transaction()` for a
single-row write in under 10 ms median on local NVMe; CI runners can
relax to 50 ms via `HUNGERLOOP_PERF_BUDGET_MS`.

**NFR-3.** The system shall not load the entire `events` table into
memory for any read; `list_events` and `list_loop_traces` use indexed
queries returning at most the requested limit.

### 3.2 Concurrency

**NFR-4.** The system shall support concurrent readers (WAL) and
serialise writers via SQLite's default locking + `BEGIN IMMEDIATE`.

**NFR-5.** The system shall not require a separate lock daemon; the
`task_locks` row is the only cross-process coordination primitive.

### 3.3 Migration safety

**NFR-6.** The system shall apply migrations forward-only via the
shipped `SQLiteMigrator`; no down-migration files are loaded
(enforced by `_DOWN_MIGRATION_RE`).

**NFR-7.** The system shall preserve at least three sibling backups
under `<db>.bak.v*` per the shipped retention policy; older backups
move to `<workspace>/.archive/`.

**NFR-8.** When a migration fails inside `BEGIN IMMEDIATE`, the
system shall roll back, retain the backup, and raise
`MigrationFailedError(version, cause, statement)` with the failing
SQL preserved (post-71f668c hardening).

### 3.4 Security

**NFR-9.** The system shall use `?` parameter binding for every
query; no string interpolation of user-supplied values into SQL.

**NFR-10.** The system shall create the database file with mode
`0600` (operator-only) and `${HUNGERLOOP_HOME}` with mode `0700`.

**NFR-11.** The system shall not log the contents of `payload_json`
columns at INFO level — payloads may contain prompt fragments that
echo task input.

### 3.5 Observability

**NFR-12.** The system shall include `db_path` and a redacted
`task_id` in every `MigrationFailedError` / lock-stolen event, but
shall not include API keys or full message contents.

## 4. Acceptance criteria

### 4.1 Fresh DB happy path

```
Given no blackboard.sqlite exists at the default path,
When the operator runs `hungerloop new "demo task" --accept-file accept.yaml`,
Then the system creates ${HUNGERLOOP_HOME}/blackboard.sqlite with mode 0600,
And applies migrations v1 + v2,
And persists the new task row,
And exits 0 within 500 ms.
```

### 4.2 Run + status + report end-to-end

```
Given a fresh DB and a registered task,
When the operator runs `hungerloop run <task_id> --model-config dummy.yaml`,
Then the system acquires the task lock,
And the orchestrator drives the loop until DONE,
And persists best_state, accepted_checks, loop_traces, stop_report, usage_snapshot,
And releases the task lock on clean exit,
And exits 0.

Given the prior task has stopped DONE,
When the operator runs `hungerloop status <task_id>` in a fresh process,
Then the system prints stop_reason=done, the best_state_id from disk,
And total_cost_usd, total_tokens matching the prior process's snapshot,
And exits 0 within 200 ms median.
```

### 4.3 Cross-process restart parity

```
Given a process P1 wrote (task_id, best_state_id="STATE-1", loop_count=5,
       accepted_check_keys=["H-001:0","H-001:1"], total_cost_usd=0.42)
       and exited cleanly,
When a fresh process P2 opens the same db and reads each value via the protocol,
Then P2 observes the same task_id,
And the same best_state_id,
And the same loop_count,
And the same accepted_check_keys set,
And the same total_cost_usd within float tolerance.
```

### 4.4 Cross-process lock contention

```
Given process P1 has acquired the task lock for <task_id>,
When process P2 calls acquire_task_lock(<task_id>, P2_owner) without --steal-lock,
Then P2 receives "held_live",
And the CLI exits 3 with the documented "wait or pass --steal-lock" message,
And P1's lock row is unchanged.
```

### 4.5 Stale-lock + steal recovery

```
Given P1 acquired the lock and crashed (lock row has locked_at=2h ago),
When P2 runs `hungerloop run <task_id> --steal-lock`,
Then the system writes a `lock_stolen` event with prev_owner=P1, new_owner=P2,
And P2 proceeds through the orchestrator,
And exits 0.
```

### 4.6 Migration on outdated DB

```
Given a SQLite file at user_version=1 (v1__initial.sql applied; v2 not yet),
When a write-capable command opens it,
Then the system applies v2__memory_candidate_lifecycle.sql under BEGIN IMMEDIATE,
And bumps user_version to 2,
And retains a sibling backup at <db>.bak.v1.<utc>,
And exits 0.

Given the same outdated file,
When a read-only command (`status` / `report` / `trace`) opens it,
Then the system raises ReadOnlyDbOutdatedError,
And the CLI prints "Run 'hungerloop run' once to apply pending migrations",
And exits 4.
```

### 4.7 Schema-too-new refusal

```
Given a SQLite file at user_version=99,
When any command opens it,
Then the system raises SchemaTooNewError,
And the CLI prints "Downgrade is not supported — restore from backup",
And exits 4.
```

### 4.8 Behavioural parity test

```
Given the protocol-parity test suite parametrized over
       [InMemoryRepository, SQLiteRepository],
When every test runs against both backends,
Then every assertion passes against both,
And no test relies on backend-specific internals.
```

### 4.9 Performance budget

```
Given a fixture task with 100 loops + 100 evidence rows + 5 best-state promotions
       persisted in SQLite,
When `hungerloop status <task_id>` runs 5 times back-to-back,
Then the median wall-clock time is under 200 ms.

Given the same fixture,
When `hungerloop report <task_id>` runs 5 times back-to-back,
Then the median wall-clock time is under 200 ms.
```

### 4.10 Read-only filesystem refusal

```
Given the resolved blackboard.sqlite path is on a read-only mount,
When the operator runs a write-capable command,
Then the CLI prints "Database is read-only; cannot run write command",
And exits 4,
And does not create or modify any files.
```

## 5. Error handling

| Condition | Behaviour | Exit code | Event |
|---|---|---|---|
| `db_path` parent dir missing | Create `${HUNGERLOOP_HOME}` with `0700`, retry | 0 | none |
| `db_path` on read-only FS, write command | `ClickException("Database is read-only…")` | 4 | none |
| `user_version > LATEST_VERSION` | `SchemaTooNewError` | 4 | none |
| `user_version < LATEST_VERSION`, write-capable | Apply pending migrations | 0 | none |
| `user_version < LATEST_VERSION`, read-only | `ReadOnlyDbOutdatedError` | 4 | none |
| Migration failure (broken SQL, FK violation) | `MigrationFailedError(version, cause, statement)`; backup retained | 5 | none |
| `down_v*.sql` file present | `DownMigrationDisallowed` | 5 | none |
| Concurrent live lock | `held_live` outcome | 3 | none |
| Stale lock without `--steal-lock` | `held_stale` outcome | 6 | none |
| Stolen lock | `stolen` outcome; proceed | 0 | `lock_stolen` |
| Process crash mid-transaction | SQLite WAL recovery on next open; partial write rolled back | n/a (next process exit code) | none |
| `transaction()` block raised | `ROLLBACK`; re-raise original exception | propagated | none |
| Concurrent write contention exceeding `busy_timeout` | `sqlite3.OperationalError("database is locked")`; bubble to caller | 1 | none |

## 7. Risks and mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| SQLite WAL needs disk flush; slow on networked filesystems | Medium | Document that `${HUNGERLOOP_HOME}` should be local; refuse to open if `statvfs` reports network FS via a clear error. |
| Connection-per-thread means leaks if threads are reused | Medium | `threading.local` cleanup in `close()`; integration test that opens 100 threads and asserts `lsof` count returns to baseline after `close()`. |
| `BEGIN IMMEDIATE` blocks readers if a writer holds for >5s | Low | `busy_timeout=5000` is generous for normal load; long-running writes are a code smell to diagnose, not work around. |
| Pydantic v2 datetime serialization to ISO-8601 string for `expires_at`; round-trip on read | Medium | Pin via parity test in B2-11: write a `MemoryCandidate` with `expires_at` set, read back, assert `==`. |
| Cross-process file lock semantics differ on Windows | Low | v0.5b.2 declares Linux/macOS support only; document in README. Windows tracked as a separate issue for v0.6. |
| Migration v2's `idx_memory_state` doesn't exist on a fresh-v1 DB after rollback | Low | The chain test in B2-15 covers this; manual recovery doc points operators to `<db>.bak.v1.*`. |
