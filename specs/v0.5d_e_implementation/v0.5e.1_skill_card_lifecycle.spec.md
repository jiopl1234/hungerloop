# v0.5e.1 — SkillCard Lifecycle

**Release:** v0.5e.1
**PRD:** `hungerloop_v0_5d_e_prd_revised.md` §15.1, §18, §19, §20.4
**Depends on:** v0.5e.0 memory lifecycle
**Status:** spec → ready to implement once v0.5e.0 ships

---

## 1. Overview

### 1.1 What

Land the candidate / active split for `SkillCard`. The shipped
v0.5a `SkillCard` is single-tier (`skill_id` + `name` + `steps`);
v0.5e.1 adds `SkillCardCandidate` (the pre-approval row) and
`ActiveSkillCard` (post-approval), both with deterministic
derivation per PRD §18.4 (no LLM in the path), plus the
`hungerloop skill approve/reject/export/import` CLI. Migration v5's
skill section ships here (the v0.5e.0 memory section already
shipped, so v5 file gets appended in the same migration but the
PRAGMA bump stays at 5 — see FR-1).

### 1.2 Why

Today's `SkillManager.maybe_create_skill_card` writes to
`SkillCard` immediately when conditions are met. That makes every
auto-generated skill instantly "live" — there's no review gate.
v0.5e.1 splits that into:

- **Candidate** — auto-generated by the orchestrator when PRD
  §15.2 trigger rule fires.
- **Active** — created by an operator running `skill approve`.

Plus `export skill.yaml` / `import skill.yaml` so skills can move
between operator machines without round-tripping through the DB.

### 1.3 User value

- **Operators**: every successful task auto-generates a candidate,
  not a live skill. No accidental pollution.
- **Reviewers**: same audit trail pattern as memory candidates;
  consistent CLI shape.
- **Cross-machine**: `skill export` / `import` for sharing curated
  skills (matches MCP-server ergonomics if downstream tools want
  to consume).

### 1.4 Non-goals

- Semantic skill retrieval (vector search → v0.6+).
- LLM-driven skill derivation (deterministic only — see PRD §18.4
  algorithms).
- Auto-activation (must be human-approved).
- Cross-task skill recall during `run` (v0.6).

## 2. Functional requirements (EARS)

### 2.1 SkillCardCandidate model

**FR-1.** The system shall add `SkillCardCandidate` per PRD §18.3:

```python
class SkillCardCandidate(BaseModel):
    skill_candidate_id: str
    task_id: str
    source_best_state_id: str
    source_stop_report_id: str | None = None

    name: str
    description: str

    trigger_signals: list[str] = Field(default_factory=list)
    preconditions: list[str] = Field(default_factory=list)
    steps: list[str] = Field(default_factory=list)

    tools_used: list[str] = Field(default_factory=list)
    accepted_check_keys: list[str] = Field(default_factory=list)
    artifact_ids: list[str] = Field(default_factory=list)
    evidence_ids: list[str] = Field(default_factory=list)

    known_failures: list[str] = Field(default_factory=list)
    reuse_notes: list[str] = Field(default_factory=list)

    state: Literal["candidate", "active", "rejected", "deprecated"] = "candidate"
    created_at: datetime
```

**FR-2.** The shipped v0.5a `SkillCard` model shall remain unchanged
in `models/skill.py`. v0.5e.1 callers read from
`active_skill_cards`, not `skill_cards` — the legacy table is
preserved for v0.5a compatibility but not extended.

### 2.2 ActiveSkillCard model

**FR-3.** The system shall add `ActiveSkillCard`:

```python
class ActiveSkillCard(BaseModel):
    skill_id: str
    source_candidate_id: str

    name: str
    description: str

    trigger_signals: list[str]
    preconditions: list[str]
    steps: list[str]

    tools_used: list[str]
    accepted_check_keys: list[str]
    artifact_ids: list[str]
    evidence_ids: list[str]
    known_failures: list[str]
    reuse_notes: list[str]

    activated_at: datetime
    activated_by: str
```

### 2.3 Trigger rule (deterministic, 5 boolean conditions)

**FR-4.** The system shall create a `SkillCardCandidate` if and
only if ALL of the following hold (PRD §15.2):

```
1. stop_report.stop_reason == StopReason.DONE
2. final BestState exists for the task
3. len(best.accepted_check_keys) >= 2
4. at least one tool_call_succeeded evidence row exists for the task
5. the final committed LoopTrace's regressed_check_keys is empty
```

If any condition fails, the system shall NOT create a candidate. No
LLM calls; no fuzzy logic. Pin via `test_skill_card_trigger.py`
parametrized over each failure mode.

**FR-5.** When the trigger fires, the system shall use the
deterministic helpers from PRD §18.4:

```
derive_name(best_state) -> str
derive_trigger_signals(best_state, traces) -> list[str]
derive_preconditions(best_state, traces) -> list[str]
derive_steps(traces) -> list[str]
derive_tools(traces, repo) -> list[str]
derive_failures(task_id, repo) -> list[str]
```

Each helper's algorithm is the pseudocode in PRD §18.4. Tests
verify byte-identical output across two runs against the same
fixture (the determinism guarantee).

### 2.4 SkillManager update

**FR-6.** The shipped `SkillManager.maybe_create_skill_card` shall
be replaced with a version that:

1. Evaluates the FR-4 conditions.
2. If true, calls the FR-5 helpers and constructs a
   `SkillCardCandidate` (NOT a `SkillCard`).
3. Persists via `repo.save_skill_card_candidate`.
4. Emits `skill_card_candidate_created` event.

**FR-7.** When the trigger does NOT fire, the system shall return
`None` and emit no event. The shipped behavior of returning `None`
is preserved.

**FR-8.** The legacy `repo.save_skill_card` path shall remain
functional for any code still constructing `SkillCard` directly,
but `SkillManager` no longer uses it. CLI `skill list` reads from
`active_skill_cards` only.

### 2.5 Skill lifecycle CLI

**FR-9.** The system shall ship the following commands:

```
hungerloop skill list [--state <S>]
hungerloop skill show <skill_candidate_id_or_skill_id>
hungerloop skill approve <skill_candidate_id> [--activated-by <name>]
hungerloop skill reject <skill_candidate_id> --reason <reason>
hungerloop skill export <skill_id> --output <path.yaml>
hungerloop skill import <path.yaml>
```

**FR-10.** When `skill approve <skill_candidate_id>` runs, the
system shall:

1. Load the candidate; refuse if state ≠ `candidate`.
2. Generate a fresh `skill_id = f"SKILL-{uuid8}"`.
3. Insert an `ActiveSkillCard` row with all candidate fields
   copied + `activated_at=now()`, `activated_by=<name|"unknown">`.
4. Update candidate state to `active`.
5. Emit `skill_card_activated` event.

**FR-11.** When `skill reject` runs, the system shall set candidate
state to `rejected`. The `--reason` flag is mandatory; missing it
is a usage error.

**FR-12.** The system shall implement `skill export <skill_id>` to
write a YAML file with the full `ActiveSkillCard` payload.

```yaml
# skill_id used as filename hint, not data
schema_version: "1"
skill_id: SKILL-abc12345
name: "..."
description: "..."
trigger_signals: ["..."]
preconditions: ["..."]
steps: ["..."]
tools_used: ["bash", "edit_file"]
accepted_check_keys: ["H-001:0", "H-001:1"]
artifact_ids: ["art-1"]
evidence_ids: ["ev-1", "ev-2"]
known_failures: []
reuse_notes: ["..."]
activated_at: "2026-05-04T12:00:00Z"
activated_by: "alice"
```

**FR-13.** When `skill import <path.yaml>` runs, the system shall:

1. Load the YAML; reject if `schema_version != "1"`.
2. Validate every field against the `ActiveSkillCard` model.
3. Generate a fresh `skill_id` (do NOT reuse the imported one to
   avoid PK collisions).
4. Insert the row with `activated_at=now()`,
   `activated_by="<imported_from_file>"`.
5. The `source_candidate_id` is set to a synthetic
   `IMPORTED-<uuid8>` (no candidate row exists for imported skills).
6. Emit `skill_card_imported` event with the source path.

**FR-14.** The `skill list` command shall accept `--state <S>` to
filter (`candidate` / `active` / `rejected` / `deprecated` / `all`).
Default `all`.

### 2.6 Migration v5 (skill section)

**FR-15.** The system shall append the FR-1 / FR-3 tables to the
v0.5e.0-shipped `migrations/v5__memory_skill_lifecycle_extensions.sql`.
Since v0.5e.0 already moved `LATEST_VERSION` to 5, v0.5e.1 does NOT
bump it again — both increments share v5.

**Important:** because v0.5e.0 already shipped v5 to operators,
v0.5e.1 cannot edit the existing v5 file in place. Instead, ship
`migrations/v5_addendum__skill_tables.sql` if v0.5e.0's v5 has
already reached production. If v0.5e.0 has NOT shipped externally
yet (still in same dev cycle), append directly.

The implementation TODO has a decision branch (E1-01) on which path
applies.

### 2.7 Event vocabulary (additive)

**FR-16.** The system shall add the following members to
`EventType`:

```
SKILL_CARD_CANDIDATE_CREATED  = "skill_card_candidate_created"
SKILL_CARD_ACTIVATED          = "skill_card_activated"
SKILL_CARD_REJECTED           = "skill_card_rejected"

```

The shipped `SKILL_CARD_EMITTED` remains unchanged but is no longer
emitted by `SkillManager` (legacy callers may still use it).

## 3. Non-functional requirements

**NFR-1.** Determinism: running the FR-5 helpers against the same
fixture twice in a row shall produce byte-identical
`SkillCardCandidate` JSON serializations. Pin via the §18.5 golden
test.

**NFR-2.** No-LLM guarantee: the `SkillManager.maybe_create_skill_card`
path shall not call `model_client.complete_json` or any other LLM
entry point. Add a unit test that asserts no `httpx` calls fire
during candidate generation.

**NFR-3.** Performance: candidate generation (all five FR-5
helpers) shall complete in under 100 ms median against a task with
50 LoopTraces and 100 evidence rows.

**NFR-4.** Performance: `skill list` shall return in under 200 ms
median against a DB with 100 candidates + 50 active skills.

**NFR-5.** YAML import safety: the import path shall use
`yaml.safe_load`, NOT `yaml.load`. The CLI shall refuse files that
deserialize to non-mappings.

**NFR-6.** Approval transactions: `skill approve` mutations execute
inside `repo.transaction()` so a crash leaves either the candidate
state-updated AND the ActiveSkillCard inserted, or neither.

## 4. Acceptance criteria

### 4.1 Trigger rule positive case

```
Given a task that ends with stop_reason=DONE,
   final BestState with accepted_check_keys=["H-001:0","H-001:1"],
   one tool_call_succeeded evidence row,
   final committed LoopTrace with empty regressed_check_keys,
When SkillManager.maybe_create_skill_card runs,
Then a SkillCardCandidate is persisted,
And state="candidate",
And accepted_check_keys=["H-001:0","H-001:1"],
And tools_used contains the tool name from the evidence row,
And a skill_card_candidate_created event is emitted.
```

### 4.2 Trigger refuses on regression

```
Given the same fixture but the final LoopTrace has
   regressed_check_keys=["H-001:0"],
When the manager runs,
Then no candidate is persisted,
And no event is emitted,
And the function returns None.
```

### 4.3 Trigger refuses with <2 accepted checks

```
Given a task with accepted_check_keys=["H-001:0"] (only one),
When the manager runs,
Then no candidate is persisted.
```

### 4.4 Trigger refuses without tool evidence

```
Given a task that completed without any tool_call_succeeded events,
When the manager runs,
Then no candidate is persisted.
```

### 4.5 Determinism golden test

```
Given a fixed fixture: 3 committed loops with delta_summary
   "deltaA","deltaB","deltaC", 2 rejected loops, 5 successful
   tool_call evidence rows distributing across the loops as
   {loop1:[t_a], loop3:[t_b,t_c], loop5:[t_a,t_a,t_b]},
   1 tool_call_failed event in loop4 with error_type="timeout",
When SkillManager.maybe_create_skill_card runs twice,
Then both runs produce candidates with byte-identical:
  steps == ["deltaA","deltaB","deltaC"]
  tools_used == ["t_a","t_b","t_c"]
  known_failures == ["tool_call_failed: timeout (loop 4)"]
  preconditions has length 2
  trigger_signals is sorted lexicographically.
```

### 4.6 No-LLM guarantee

```
Given an httpx mock that fails any request,
When SkillManager.maybe_create_skill_card runs against the §4.1 fixture,
Then no httpx call fires,
And the candidate is generated successfully.
```

### 4.7 approve happy path

```
Given a SkillCardCandidate in state="candidate",
When `skill approve <id> --activated-by alice` runs,
Then an ActiveSkillCard row exists with source_candidate_id=<id>,
And candidate.state="active",
And skill_id starts with "SKILL-",
And a skill_card_activated event exists,
And exit code is 0.
```

### 4.8 export / import round-trip

```
Given an ActiveSkillCard with skill_id=SKILL-abc12345,
When `skill export SKILL-abc12345 --output /tmp/skill.yaml` runs,
Then /tmp/skill.yaml is created with schema_version="1",
And exit code is 0.

Given the YAML file from above,
When `skill import /tmp/skill.yaml` runs (against a fresh DB),
Then a new ActiveSkillCard row exists,
And new_skill_id != original (FR-13 step 3),
And every other field round-trips,
And source_candidate_id starts with "IMPORTED-",
And a skill_card_imported event exists.
```

### 4.9 import refuses unknown schema

```
Given a YAML file with schema_version="2",
When `skill import` runs,
Then stderr contains "Unsupported schema_version: 2",
And exit code is 2,
And no row is inserted.
```

### 4.10 Migration v5 skill tables present

```
Given a SQLite file post-v0.5e.1 ship,
When `repo.list_skill_card_candidates()` is called,
Then the call succeeds (table exists),
And the table has the FR-1 columns,
And `active_skill_cards` table exists with FR-3 columns.
```

## 5. Error handling

| Condition | Behaviour | Exit code | Event |
|---|---|---|---|
| Trigger rule fails any of the 5 conditions | Return None silently | n/a | none |
| `skill approve` on missing candidate | "Candidate not found"; stderr | 1 | none |
| `skill approve` on already-active candidate | "Already activated as <skill_id>"; stderr | 2 | none |
| `skill approve` on rejected candidate | "Cannot activate rejected candidate"; stderr | 2 | none |
| `skill reject` without --reason | Click usage error | 2 | none |
| `skill export` on missing skill_id | "Skill not found"; stderr | 1 | none |
| `skill export` to unwritable path | OSError → click error | 4 | none |
| `skill import` on missing file | "File not found"; stderr | 1 | none |
| `skill import` with malformed YAML | "YAML parse error: <msg>"; stderr | 2 | none |
| `skill import` with non-mapping root | "YAML root must be a mapping"; stderr | 2 | none |
| `skill import` with schema_version != "1" | "Unsupported schema_version"; stderr | 2 | none |
| `skill import` with missing required fields | Pydantic validation error | 2 | none |
| Concurrent approval (two operators race) | Task lock serialises | depends | per outcome |
| Migration v5_addendum / appended-to-v5 fails | `MigrationFailedError`; backup retained | 5 | none |
| `is_reusable`-style false positives in derive_failures | Documented; future helper iteration | 0 | none |

## 7. Risks and mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Migration strategy decision (E1-01) ships wrong path → operator DBs corrupt | High | Ship Path B if v0.5e.0 has reached any external user; the migrator extension is small and the cost of being wrong is high. |
| Determinism breaks when iteration order changes (Python dict vs set) | Medium | Helpers explicitly sort outputs; golden test catches order regressions. |
| `derive_steps` produces ambiguous text from terse `delta_summary` | Low | Fall-back text "Loop N: committed candidate <id>" guarantees a non-empty step. Operator-edited skills can override post-import. |
| `skill import` from a malicious YAML triggers code execution | Critical | `yaml.safe_load` only; ban `!!python/` tags. Tested via NFR-5. |
| Imported skill's `source_candidate_id="IMPORTED-..."` doesn't FK-resolve | Low | The FK in the v5 schema references `skill_card_candidates(skill_candidate_id)`. For imports we either drop the FK (move column to nullable) or insert a synthetic candidate row. Recommendation: nullable FK. |
| `SKILL_CARD_EMITTED` legacy event still fires from non-orchestrator paths, polluting audit | Low | Document that `SKILL_CARD_EMITTED` is deprecated; add a deprecation warning when callers use the legacy `repo.save_skill_card`. |
| `skill approve` and `skill_card_candidate_created` race when v0.6 auto-approve lands | Future | Out of scope for v0.5e.1; gate approval via task lock + state check (already done). |
