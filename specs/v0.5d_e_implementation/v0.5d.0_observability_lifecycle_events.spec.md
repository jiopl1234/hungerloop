# v0.5d.0 — Observability + Lifecycle Events

**Release:** v0.5d.0
**PRD:** `hungerloop_v0_5d_e_prd_revised.md` §5–§11
**Depends on:** v0.5b.2 SQLiteRepository hard gate
**Status:** spec → ready to implement once v0.5b.2 ships

---

## 1. Overview

### 1.1 What

Make HungerLoop *explainable*. The orchestrator gains a fixed event
firing order (§7.5), `LoopTrace`/`StopReport` get additive list
fields, `RepositoryProtocol` grows the observability methods
(`list_events`, `list_loop_traces` with kwargs, `iter_accepted_checks`,
etc.), CLI commands stop reading private repo state, and SQLite
gets a v3 (table) + v4 (indexes) migration pair.

### 1.2 Why

Today: `report_format.py` reaches into `_stop_reports_history`,
`trace_cmd.py` into `_events`, `repair_state.py` into four private
attrs. Every one of those silently degrades to "everything is fine"
the moment SQLiteRepository ships, because `getattr(sqlite_repo,
"_events", None)` returns `None`. v0.5d.0 is the cleanup that turns
private-field reads into formal protocol calls and makes the
orchestrator's event log a first-class wire contract.

### 1.3 User value

- **Operators**: `hungerloop trace export <task_id>` shows the full
  loop lifecycle (planned → worker_started → tool_call_succeeded → …
  → committed) instead of just three coarse events.
- **CI/dashboards**: the JSONL stream is now machine-rich enough to
  drive Prometheus-style aggregations without parsing free-text
  `delta_summary`.
- **Future v0.5d.1 / v0.5e**: every downstream feature relies on the
  protocol methods landed here.

### 1.4 Non-goals

- Resume-preflight ERROR gate (v0.5d.1).
- repair-state D8-D13 (v0.5d.1).
- MemoryCandidate predicate fields / approve CLI (v0.5e.0).
- SkillCardCandidate (v0.5e.1).
- LLM-driven anything.

## 2. Functional requirements (EARS)

### 2.1 Protocol additions

**FR-1.** The system shall extend `RepositoryProtocol` with the
methods enumerated in PRD §6.2:

```
task_exists, get_task_status, set_task_status,
append_event(EventRecord) (existing kwargs form preserved as overload),
list_events(task_id, *, since_loop, until_loop, event_types, include_global),
get_loop_trace, list_loop_traces(task_id, *, limit, reverse),
get_last_stop_report, list_stop_reports,
save_hunger_snapshot, get_latest_hunger_snapshot,
save_usage_snapshot, get_usage_snapshot (existing) — semantics unchanged,
list_candidates_for_task, get_candidate,
iter_accepted_checks, validation_exists, get_validation_report,
get_task_lock,
list_model_errors, list_tool_errors,
list_successful_tool_call_evidence
```

**FR-2.** `InMemoryRepository` and `SQLiteRepository` shall both
implement every method in FR-1. The shipped private-attribute paths
(`_events`, `_stop_reports_history`, etc.) remain in InMemory for
test convenience but are no longer the primary read path.

**FR-3.** When `list_events(include_global=False)` is called, the
system shall return only rows where `events.task_id = <task_id>`.
When `include_global=True`, the system shall additionally return
rows where `events.task_id IS NULL`.

**FR-4.** When `list_loop_traces(task_id, limit=N, reverse=True)` is
called, the system shall return at most `N` traces ordered by
`loop_id DESC`. The default (`limit=None, reverse=False`) preserves
the shipped chronological-ascending behavior.

### 2.2 Event vocabulary expansion (additive only)

**FR-5.** The system shall add the following members to `EventType`
without renaming or removing any shipped value:

```
LOOP_PLANNED
WORKER_STARTED, WORKER_FINISHED, WORKER_FAILED
MODEL_CALL_STARTED, MODEL_CALL_SUCCEEDED, MODEL_CALL_FAILED,
MODEL_AUTH_REQUIRED, MODEL_RATE_LIMITED
TOOL_CALL_STARTED, TOOL_CALL_SUCCEEDED, TOOL_CALL_FAILED
VALIDATION_STARTED, VALIDATION_FINISHED
CHECK_PASSED, CHECK_FAILED, CHECK_REGRESSED
CANDIDATE_CREATED, CANDIDATE_COMMITTED, CANDIDATE_REJECTED
STOP_REPORT_CREATED
ERROR
```

**FR-6.** When the orchestrator processes a single loop, the system
shall emit events in the order pinned by PRD §7.5:

```
LOOP_STARTED → LOOP_PLANNED → (WORKER_STARTED → tool/model calls →
WORKER_FINISHED|FAILED)+ → CANDIDATE_CREATED → VALIDATION_STARTED →
(CHECK_PASSED|FAILED|REGRESSED)+ → VALIDATION_FINISHED →
CANDIDATE_COMMITTED|REJECTED → LOOP_COMMITTED|LOOP_REJECTED.
```

**FR-7.** When a loop short-circuits via `SAFETY_STOP` /
`HUMAN_REQUIRED` / `ERROR`, the system shall preserve whichever
events have already fired and emit the stop event followed by
`STOP_REPORT_CREATED`. No "rollback" of already-written event rows.

### 2.3 LoopTrace v2 (additive)

**FR-8.** The system shall add the following fields to `LoopTrace`,
each defaulting to its empty value so old rows deserialise cleanly:

```python
best_state_id_before_loop: str | None = None
best_state_id_after_loop: str | None = None
verdict: str | None = None
currently_passed_check_keys: list[str] = []
satisfied_hunger_item_ids: list[str] = []
unsatisfied_hunger_item_ids: list[str] = []
model_errors: list[str] = []
tool_errors: list[str] = []
worker_errors: list[str] = []
```

**FR-9.** When the orchestrator's loop body raises an exception, the
system shall still persist a `LoopTrace` with `stop_reason=ERROR`,
`worker_errors` populated from the caught exception, and an
accompanying `StopReport`. (Closes the synthetic-worker-exception
gap.)

### 2.4 StopReport v2 (additive)

**FR-10.** The system shall add the following fields to `StopReport`
without renaming `recommendation`:

```python
accepted_check_keys: list[str] = []
llm_calls: int = 0
tool_calls: int = 0
last_validation_report_id: str | None = None
last_loop_id: int | None = None
recommended_next_actions: list[str] = []
resume_hint: str | None = None
```

**FR-11.** When `StopReport.resume_hint` is unset by the writer, the
system shall populate it from the `STOP_REASON_HINTS` map keyed by
`stop_reason.value` (PRD §9.3).

### 2.5 UsageSnapshot persistence

**FR-12.** The system shall persist `UsageSnapshot` rows in the
`usage_snapshots` table created by migration v3.

**FR-13.** When `BudgetGuard.record_llm_usage(task_id, usage)` is
called, the system shall upsert the corresponding `usage_snapshots`
row (incrementing `total_tokens`, `total_cost_usd`, `llm_calls`,
updating `last_loop_id`).

**FR-14.** When `ToolHarness` records a tool call, the system shall
increment `usage_snapshots.tool_calls` (and `tool_errors` on
failure).

### 2.6 CLI no-private-fields cleanup

**FR-15.** The system shall remove every `getattr(repo, "_<attr>")`
read from `cli/report_format.py`, `cli/trace_cmd.py`,
`cli/repair_state.py`, and `cli/status_cmd.py`. Reads route through
the protocol methods landed in FR-1.

**FR-16.** When the CLI cannot satisfy a read because a protocol
method does not exist, the system shall raise `NotImplementedError`
explicitly rather than silently returning empty data — guards
against the "everything is fine" degradation pattern noted in the
post-71f668c review.

### 2.7 SQLite migrations

**FR-17.** The system shall ship `migrations/v3__usage_snapshots.sql`
creating the `usage_snapshots` table per PRD §11.2.

**FR-18.** The system shall ship `migrations/v4__observability_indexes.sql`
creating the indexes per PRD §11.3.

**FR-19.** The system shall bump `SQLiteMigrator.LATEST_VERSION` to 4
exactly once (after both v3 and v4 are committed); intermediate
states are not shipped.

**FR-20.** When opening a database with `user_version=2` (post-c0-01),
the system shall apply v3 then v4 in sequence, retain a backup at
each step per the shipped retention policy, and bump to
`user_version=4`.

## 3. Non-functional requirements

**NFR-1.** Performance: `list_events(task_id, limit=100)` shall
return in under 50 ms median against a task with 10k events
(indexed via `idx_events_task_loop`). Larger windows scale linearly
with the result set.

**NFR-2.** Performance: `list_loop_traces(task_id)` shall return in
under 100 ms median against a task with 1k traces.

**NFR-3.** The 200 ms `report` / `status` budget from c1-01 shall
hold; the new fields on LoopTrace v2 / StopReport v2 are JSON-blob
columns, not new joins.

**NFR-4.** The orchestrator event firing path shall not block the
loop body for more than 5 ms per event; events go through
`repo.append_event` which is a single-row INSERT inside the existing
transaction boundary.

**NFR-5.** Migrations v3 + v4 shall apply against a freshly-promoted
`user_version=2` DB in under 2 seconds total on local NVMe.

**NFR-6.** No event payload shall include API keys, raw model
prompts, or full message contents. `MODEL_CALL_FAILED` includes
`error_type` (a stable enum-like string) and `error_message`
truncated to 240 chars.

## 4. Acceptance criteria

### 4.1 Full lifecycle event order

```
Given a task with no prior events,
When the orchestrator runs one full loop ending in a successful commit,
Then `list_events(task_id)` returns rows in this exact event_type order:
  loop_started, loop_planned, worker_started, tool_call_started,
  tool_call_succeeded, model_call_started, model_call_succeeded,
  worker_finished, candidate_created, validation_started, check_passed,
  validation_finished, candidate_committed, loop_committed,
And every row has the same task_id and matching loop_id.
```

### 4.2 Synthetic worker exception persists trace

```
Given the orchestrator is mid-loop and the worker raises RuntimeError("boom"),
When the loop's outer error handler runs,
Then a LoopTrace row exists with stop_reason=ERROR
And worker_errors contains "RuntimeError: boom",
And a StopReport row exists with stop_reason=ERROR,
And resume_hint is "Inspect trace/report, repair state, then resume or reset.",
And the orchestrator releases the task lock cleanly,
And the CLI exit code is 7 (ERROR).
```

### 4.3 CLI no longer reads private fields

```
Given an SQLiteRepository with task data persisted,
When `hungerloop status <task_id>`, `hungerloop report <task_id>`,
     `hungerloop trace <task_id>`, and `hungerloop repair-state <task_id> --check`
     each run successfully against the SQLiteRepository,
Then no command path executes a `getattr(repo, "_*")` access,
And every read goes through a documented protocol method.
```

### 4.4 list_events filtering

```
Given a task with 50 events: 30 task-scoped, 20 global (task_id IS NULL),
When `list_events(task_id, include_global=False)` is called,
Then exactly 30 rows are returned.

When `list_events(task_id, include_global=True)` is called,
Then exactly 50 rows are returned.

When `list_events(task_id, event_types=["loop_committed"])` is called,
Then only loop_committed rows are returned.

When `list_events(task_id, since_loop=5, until_loop=10)` is called,
Then only rows with 5 <= loop_id <= 10 are returned.
```

### 4.5 list_loop_traces ordering and limit

```
Given a task with 50 LoopTrace rows (loop_id 1..50),
When `list_loop_traces(task_id)` is called,
Then 50 rows are returned in ascending loop_id order.

When `list_loop_traces(task_id, limit=5, reverse=True)` is called,
Then exactly 5 rows are returned in descending loop_id order: 50,49,48,47,46.
```

### 4.6 UsageSnapshot persists across restart

```
Given process P1 records 3 LLM calls totalling 5000 tokens / $0.12,
When P1 exits cleanly,
And process P2 calls `repo.get_usage_snapshot(task_id)`,
Then P2 observes total_tokens=5000, total_cost_usd≈0.12, llm_calls=3,
And `last_loop_id` matches P1's most recent loop.
```

### 4.7 Migration v3 + v4 applied cleanly

```
Given a SQLite file at user_version=2 (post-c0-01),
When SQLiteRepository.open() runs,
Then migrations v3 and v4 apply in sequence,
And `usage_snapshots` table exists,
And every documented index from PRD §11.3 exists,
And user_version=4,
And two sibling backups exist (one per migration step).
```

### 4.8 LoopTrace v2 forward-compat

```
Given a stored LoopTrace row written by c0-01 (no v2 list fields),
When v0.5d.0 code reads it back,
Then deserialization succeeds,
And currently_passed_check_keys, satisfied_hunger_item_ids,
   model_errors, tool_errors, worker_errors are each [].
```

## 5. Error handling

| Condition | Behaviour | Exit code | Event |
|---|---|---|---|
| `list_events` against unknown task | Return `[]` (not error) | 0 | none |
| `list_loop_traces(task_id, limit=-1)` | `ValueError("limit must be >= 0")` | n/a | none |
| `set_task_status` with invalid value | `ValueError` listing valid values | n/a | none |
| Orchestrator raises during loop body | Catch in finally, persist LoopTrace+StopReport with stop_reason=ERROR | 7 | `error`, `stop_report_created` |
| `append_event` payload not JSON-serialisable | `TypeError`; orchestrator wraps in `worker_errors` | n/a | none |
| Migration v3 fails (FK violation) | `MigrationFailedError(version=3, statement)`; backup retained | 5 | none |
| Migration v4 fails (existing index named differently) | `MigrationFailedError(version=4)`; backup retained | 5 | none |
| `list_loop_traces` exceeds NFR-2 budget | Log warning; do not fail; perf test catches it | 0 | none |
| CLI tries `getattr(repo, "_events")` after FR-15 | Code review / lint blocks; no runtime path remains | n/a | none |

## 7. Risks and mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Event-write inside transaction blocks the commit boundary | Medium | Pin NFR-4 (5 ms / event); add perf test that fires 100 events in one loop and measures total transaction time. |
| New events double-count vs shipped LOOP_STARTED/COMMITTED/REJECTED | Medium | §7.5 ordering test; reviewers must check that `LOOP_STARTED` precedes `WORKER_STARTED`, never duplicates worker semantics. |
| LoopTrace v2 fields balloon JSON payload size | Low | Lists default `[]`; in practice <10 entries each. Add a payload-size assertion to the perf fixture. |
| Migration v4 indexes conflict with operator-added custom indexes | Low | All new indexes use `idx_<table>_<cols>` naming; if operator's name collides they get a clear `IF NOT EXISTS` no-op (idempotent). |
| CLI cleanup misses a private-field read | Medium | Lint test (D0-11) greps for `getattr(.*repo.*"_`; CI fail. |
| Orchestrator catches exception but skips trace write | High | Use `try/finally` around the whole loop body; trace write is in `finally`, not the success branch. Covered by D0-13. |
