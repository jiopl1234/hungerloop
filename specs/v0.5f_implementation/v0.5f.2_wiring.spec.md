# v0.5f.2 — Wiring (orchestrator + worker + factory)

**Release:** v0.5f.2
**Parent design:** [`../v0.5f_loop_memory.spec.md`](../v0.5f_loop_memory.spec.md) §3.8, §3.9, §3.10
**Depends on:** v0.5f.1 ContextBuilder
**Status:** spec → ready to implement once v0.5f.1 lands

---

## 1. Overview

### 1.1 What

Three small wiring changes that turn v0.5f.1's populated
`ContextPack` into observable runtime behavior:

| Item | Lives in | What it does |
|---|---|---|
| `LoopOrchestrator` truncation event | `services/loop_orchestrator.py` | When `ContextPack.truncation_info != None`, emit `CONTEXT_TRUNCATED` before `WORKER_STARTED`. |
| `ExecutionWorker` Prior-loop block | `services/execution_worker.py` | `_messages` reads the new `ContextPack` fields and renders the parent §3.9 / FR-9 block when any trigger condition fires. |
| `orchestrator_factory` injection | `cli/orchestrator_factory.py` | Production `WorkspaceManager` flows into `ContextBuilder.__init__` as the `WorkspaceReader`. |

After v0.5f.2 ships, the cross-loop story is end-to-end:
worker prompts contain prior-loop context; truncation events
land in audit logs; existing dummy-driven tests stay green.

### 1.2 Why

v0.5f.1 produces the populated `ContextPack` but neither the
worker nor the orchestrator consumes it. v0.5f.2 closes that
loop. Three independent changes, one PR.

### 1.3 Non-goals

- Changing `ExecutionWorker.run` return shape. The block change
  is purely inside `_messages`.
- Adding new orchestrator events beyond `CONTEXT_TRUNCATED`.
  Parent FR-8 is the only new emission.
- Rewriting `_messages` from scratch. The parent §3.9 / FR-9
  block is **appended** before the existing "Required JSON shape
  example" block; everything else stays.

## 2. Functional requirements (EARS)

### 2.1 Orchestrator emits CONTEXT_TRUNCATED

**LM2-FR-1.** `LoopOrchestrator._dispatch_assignments` (or
whichever helper currently emits `WORKER_STARTED` after
`context_builder.build_for_agent`) shall, when
`context.truncation_info is not None`, append an event before
the existing `WORKER_STARTED`:

```python
context = self.context_builder.build_for_agent(
    task_id=task_id,
    loop_id=loop_id,
    agent_id=assignment.agent_id,
    mission=assignment.mission,
    target_hunger_item_ids=assignment.target_hunger_item_ids,
    budget=budget,
    allowed_tools=assignment.allowed_tools,
    output_schema_name=spec.output_schema_name,
    candidate_workspace_ref=f"candidates/loop_{loop_id:03d}",
)
if context.truncation_info is not None:
    self.repo.append_event(
        EventType.CONTEXT_TRUNCATED,
        context.truncation_info.model_dump(),
        task_id=task_id,
        loop_id=loop_id,
    )
self.repo.append_event(
    EventType.WORKER_STARTED,
    {
        "agent_id": assignment.agent_id,
        "mission": assignment.mission,
        "target_hunger_item_ids": list(
            assignment.target_hunger_item_ids
        ),
    },
    task_id=task_id,
    loop_id=loop_id,
)
```

The event ordering invariant — `CONTEXT_TRUNCATED` strictly
before `WORKER_STARTED` for the same `loop_id` — is asserted in
LM3 acceptance §4.1 of the v0.5f.3 spec; v0.5f.2 just
implements it.

### 2.2 Worker renders the Prior-loop block

**LM2-FR-2.** `ExecutionWorker._messages(context)` shall, when
the parent §3.9 / FR-9 trigger conditions fire, append the
"Prior loop context" block to the user message. Trigger:

```python
trigger = (
    context.last_self_summary is not None
    or context.failure_patterns_to_avoid
    or context.relevant_evidence_summaries
    or context.best_workspace_files
)
```

When `not trigger`, the message body is byte-identical to the
post-`0568404` v0.5e.1 output (parent FR-10 / §5.9 — the
golden test lives in v0.5f.3 LM3-01).

When `trigger`, the block format is exactly parent §3.9:

```text
Prior loop context (loop {loop_id} of this task):
- last attempt summary: {last_self_summary or 'n/a'}
- best state: {best_state_summary or 'empty'}
- files in best/: {", ".join(best_workspace_files)}
- patterns to avoid (do NOT repeat these actions; they did not move any check):
  - {failure_patterns_to_avoid[0]}
  - ...
- successful actions already on record (refer to these instead of re-running):
  - {relevant_evidence_summaries[0]}
  - ...

If a previous loop already created a file you need, prefer
patch_file over a fresh write_file.
If you already explored the workspace last loop, do NOT explore
again — act on the patterns-to-avoid above.
```

Suppression rules within the block:

- The `files in best/:` line is omitted when
  `best_workspace_files == []`.
- The `patterns to avoid` sub-block is omitted when
  `failure_patterns_to_avoid == []`.
- The `successful actions already on record` sub-block is
  omitted when `relevant_evidence_summaries == []`.
- The two trailing prose hints are emitted when ANY of the
  above sub-blocks is present (else the entire Prior-loop
  block was suppressed by the `trigger` test).

The block is **appended before** the "Required JSON shape
example" block in the user message (parent §3.9 / FR-9).

`_messages` remains a pure `@staticmethod` (or pure function)
over `ContextPack`. It does NOT receive `repo` or any I/O
handle (parent NFR-7 / FR-9).

### 2.3 orchestrator_factory wiring

**LM2-FR-3.** `cli/orchestrator_factory.py::build_orchestrator`
shall instantiate `ContextBuilder` with the production
`WorkspaceManager` as the `workspace_reader`:

```python
workspace_manager = WorkspaceManager(
    workspace_root=ctx.workspace_root,
)
context_builder = ContextBuilder(
    repo=repo,
    workspace_reader=cast(WorkspaceReader, workspace_manager),
)
```

`cast` is the project's idiom for runtime-structural conformance
without adding an explicit `WorkspaceManager(WorkspaceReader)`
inheritance (the v0.5f.1 LM1-FR-2 unit test pins that the cast
is sound).

If `WorkspaceManager` already exposes
`list_workspace_files(...)` matching the Protocol signature, no
adapter is needed. If the names diverge, add a thin wrapper
class in `orchestrator_factory.py` (example below) — do **not**
weaken the Protocol.

```python
class _WorkspaceManagerReader:
    def __init__(self, mgr: WorkspaceManager) -> None:
        self._mgr = mgr

    def list_workspace_files(
        self,
        task_id: str,
        *,
        ref: Literal["best"] | Literal["candidate"],
        loop_id: int | None = None,
    ) -> list[str]:
        return self._mgr.list_workspace_files(
            task_id, ref=ref, loop_id=loop_id
        )
```

- `tests/integration/test_recovery_full_chain.py`

## 4. Acceptance criteria

The full prompt-rendering acceptance set lives in v0.5f.3
(parent §5.1 / §5.2 / §5.2b / §5.3 / §5.9 / §5.10). v0.5f.2's
own acceptance focuses on the wiring — does the change reach
production code paths cleanly without breaking anything?

### 4.1 CONTEXT_TRUNCATED emitted on truncation

```
Given a contrived ContextPack with truncation_info != None
   (constructed by injecting a fake ContextBuilder that returns
    a pre-built pack),
When LoopOrchestrator dispatches the worker for that loop,
Then the events table has, ordered by rowid for the same loop_id:
  context_truncated  (payload == truncation_info.model_dump())
  worker_started     (payload as today)
```

### 4.2 No CONTEXT_TRUNCATED when no truncation

```
Given a normal build (truncation_info == None on the pack),
When the orchestrator dispatches,
Then NO context_truncated event is appended for that loop_id,
And worker_started fires as today.
```

### 4.3 Worker prompt parity (Loop 1)

```
Given Loop 1 of a fresh task with empty best/ and no prior
   evidence,
When ExecutionWorker._messages renders the user message,
Then the output is byte-identical to the post-0568404 v0.5e.1
   baseline string.
```

(The baseline string itself is pinned in v0.5f.3 LM3-01.)

### 4.4 Worker prompt with Prior-loop block

```
Given a ContextPack with last_self_summary set and one
   failure_patterns_to_avoid entry but empty
   relevant_evidence_summaries and empty best_workspace_files,
When ExecutionWorker._messages renders,
Then the user message contains exactly one "Prior loop context"
   header,
And contains the "patterns to avoid" sub-block,
And does NOT contain the "successful actions already on record"
   sub-block,
And does NOT contain "files in best/:" line,
And the trailing prose hints ("If a previous loop already
   created a file...") are present.
```

### 4.5 orchestrator_factory wiring

```
Given a fresh CliContext with workspace_root = some tmp_path,
When build_orchestrator is invoked,
Then the resulting orchestrator's context_builder has its
   workspace_reader attribute set to (a wrapper of) the
   WorkspaceManager constructed against tmp_path,
And calling
   orchestrator.context_builder.workspace_reader
   .list_workspace_files("missing-task", ref="best")
   returns [] without raising.
```

### 4.6 Dummy integration tests stay green

```
When the entire test suite runs after v0.5f.2 lands,
Then all six dummy integration tests pass without modification.
```
