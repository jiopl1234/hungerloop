# v0.5f.4 - Budgeted Refinement Worker Loops

**Release:** v0.5f.4
**Parent design:** [`../v0.5f_loop_memory.spec.md`](../v0.5f_loop_memory.spec.md)
**Depends on:** v0.5f.3 validation
**Status:** spec -> ready for review

---

## 1. Overview

### 1.1 What

v0.5f.4 turns the existing "hunger budget" from a stop-only
mechanism into an optional work mode:

```text
default mode:
  finish original acceptance checks -> DONE

budgeted refinement mode:
  finish original acceptance checks
  -> generate next deterministic refinement tier
  -> keep looping while user-provided loop budget remains
  -> stop when budget is exhausted, all enabled tiers are complete,
     or a real safety/human/blocking condition fires
```

The key requirement is user intent:

- `--max-loops` remains a defensive safety cap.
- A new explicit loop budget controls how many loops the worker may
  spend improving the result.
- DONE is no longer the only "good" terminal state in budgeted mode.
  A task may stop normally because the user-provided refinement budget
  was spent after base correctness was already achieved.

### 1.2 Why

The current implementation already has budget primitives:

- `HungerPolicy.max_total_cost_usd`
- `HungerPolicy.max_total_tokens`
- `DecayType.LOOP_COUNT` with `decay_duration_seconds` acting as a
  loop-count budget
- `HungerClockState.loop_count`, incremented once per accepted loop

But those primitives only decide when to stop. They do not create more
work after the original ledger is done.

Current failure modes:

1. `HungerEngine.tick()` treats `ledger.is_done()` as terminal DONE.
   This ignores any remaining user-provided loop budget.
2. When all hunger items are satisfied, `RuleBasedPlanner` has no
   active items to assign. Even if the engine did not stop, the
   orchestrator would eventually hit the empty-plan BLOCKED path.
3. The user cannot say "spend 20 loops improving this after it passes"
   in CLI terms. Current `--max-loops` is only a defensive cap.
4. Global stagnation can stop the run before the user-specified
   refinement budget is spent.
5. The existing single-shot `ExecutionWorker` is PRD-conformant for
   v0.5f, but it is weak for real coding tasks. v0.5f.4 does not solve
   intra-loop ReAct; it makes cross-loop incremental improvement
   possible and leaves ReAct for a follow-on worker release.

### 1.3 Design principle

Budgeted refinement must preserve the project's existing invariants:

- Check-level commits stay mandatory. Every promoted refinement must
  pass at least one new acceptance check.
- Workers still write only candidate workspaces. `CommitManager`
  remains the only promoter to `best/`.
- Requirement generation remains rule-based. Refinement items are not
  invented by an LLM.
- Default behavior is unchanged. Existing tasks still stop at DONE
  unless budgeted refinement mode is explicitly enabled.

### 1.4 Non-goals

- No intra-loop ReAct / tool-result feedback loop. That belongs in a
  future `ExecutionWorkerV2` or `InteractiveExecutionWorker`.
- No LLM-generated acceptance checks.
- No subjective "make it nicer" item without a deterministic check.
- No global multi-worker scheduling change.
- No change to workspace isolation or check-level commit rules.

## 2. Terms

### 2.1 Base tier

Tier 0 is the original task correctness tier. It is produced by the
existing `RequirementCompiler` and represents the user's explicit
goal and acceptance criteria.

### 2.2 Refinement tier

A refinement tier is a deterministic set of additional hunger items
generated after all lower tiers have been satisfied.

Recommended initial tiers:

- Tier 0: correctness, existing compiled requirements.
- Tier 1: regression tests and edge-case tests.
- Tier 2: static quality checks such as ruff, mypy, formatting, or
  project-specific lint commands.
- Tier 3: docs and usability checks, but only when backed by concrete
  file or shell checks.
- Tier 4: performance or polish checks, only when a benchmark or smoke
  command is configured.

v0.5f.4 only requires the framework and one deterministic built-in
profile. More profiles can land later.

### 2.3 Budgeted refinement mode

Budgeted refinement mode means:

- Base correctness is still required.
- After base correctness passes, the orchestrator may generate
  refinement-tier items.
- The run continues while loop budget remains and at least one enabled
  tier has work.
- Budget exhaustion after base correctness is not a safety failure.

## 3. Functional Requirements

### 3.1 Add explicit completion mode

**LM4-FR-1.** The system shall add a completion mode to
`HungerPolicy`:

```python
class CompletionMode(str, Enum):
    STOP_ON_DONE = "stop_on_done"
    SPEND_BUDGET = "spend_budget"


class HungerPolicy(BaseModel):
    ...
    completion_mode: CompletionMode = CompletionMode.STOP_ON_DONE
    refinement_profile: str | None = None
    max_refinement_tier: int = 0
    respect_stagnation: bool = True
```

Default values preserve current behavior:

- `STOP_ON_DONE`
- no refinement profile
- `max_refinement_tier == 0`
- stagnation still respected

When `completion_mode == STOP_ON_DONE`, `HungerEngine.tick()` and
`LoopOrchestrator.run()` shall behave exactly as v0.5f.3.

### 3.2 Add tier metadata to hunger items

**LM4-FR-2.** `HungerItem` shall gain additive metadata:

```python
refinement_tier: int = 0
refinement_kind: str = "correctness"
generated_by: str | None = None
source_check_keys: list[str] = Field(default_factory=list)
```

Rules:

- Existing items deserialize as tier 0 correctness items.
- `HungerLedger.is_done()` keeps its existing broad semantics.
- New helper methods shall be added instead of changing current helper
  behavior:

```python
def unfinished_items_by_tier(self, max_tier: int) -> list[HungerItem]: ...
def tier_is_done(self, tier: int) -> bool: ...
def all_tiers_done(self, max_tier: int) -> bool: ...
```

### 3.3 Add normal budget exhaustion stop reason

**LM4-FR-3.** The system shall add:

```python
StopReason.BUDGET_EXHAUSTED = "budget_exhausted"
```

This reason is only used when budgeted refinement mode is enabled and
base correctness has already passed.

Mapping to `GoalStatus`:

- If tier 0 is satisfied, `BUDGET_EXHAUSTED -> completed`.
- If tier 0 is not satisfied but a useful best state exists,
  `BUDGET_EXHAUSTED -> partial`.
- If no useful best state exists, `BUDGET_EXHAUSTED -> abandoned`.

`SAFETY_STOP` remains reserved for hard cost/token ceiling failures and
other safety ceilings. `HUNGER_EXPIRED` remains the legacy/default
reason for loop-count exhaustion before the base tier is done.

### 3.4 Introduce RefinementCompiler

**LM4-FR-4.** The system shall add a deterministic service:

```python
class RefinementCompiler:
    def ensure_next_tier(
        self,
        *,
        task_id: str,
        policy: HungerPolicy,
        ledger: HungerLedger,
        best_state: BestState | None,
    ) -> RefinementCompileResult: ...
```

The result shape:

```python
class RefinementCompileResult(BaseModel):
    added_item_ids: list[str] = Field(default_factory=list)
    active_tier: int | None = None
    exhausted: bool = False
    rationale: str = ""
```

The compiler shall:

- Be LLM-free.
- Never mutate `best/`.
- Generate items only for `1 <= tier <= policy.max_refinement_tier`.
- Generate a higher tier only when all lower tiers are done.
- Be idempotent. Re-running it must not duplicate items.
- Emit hunger items with real acceptance checks.
- Refuse subjective checks that cannot be validated by the existing
  acceptance runner.

### 3.5 Provide one built-in deterministic profile

**LM4-FR-5.** v0.5f.4 shall include one built-in profile named
`python_medium`.

The profile may generate only checks that are valid in the current
acceptance system:

- Tier 1: configured test command passes.
- Tier 2: configured static quality command passes.
- Tier 3: configured smoke command or documentation file check passes.

The profile shall be driven by config, not by repository guessing:

```yaml
refinement:
  profile: python_medium
  max_tier: 2
  checks:
    test:
      argv: ["python", "-m", "pytest", "-q"]
    quality:
      argv: ["ruff", "check", "."]
    typecheck:
      argv: ["mypy", "--strict", "src/"]
```

If a profile lacks a command for a tier, that tier is skipped rather
than generating a fake item.

### 3.6 Orchestrator creates refinement work before stopping on DONE

**LM4-FR-6.** `LoopOrchestrator._step_inner()` shall insert a
budgeted refinement hook before returning a DONE stop report.

Pseudo-flow:

```python
policy = repo.get_hunger_policy(task_id)
clock = repo.get_hunger_clock(task_id)
ledger = repo.get_hunger_ledger(task_id)

if policy.completion_mode == CompletionMode.SPEND_BUDGET:
    result = refinement_controller.ensure_work_or_budget_stop(
        task_id=task_id,
        policy=policy,
        clock=clock,
        ledger=ledger,
    )
    if result.stop_reason is not None:
        return self._emit_stop(task_id, result.stop_reason)
    if result.added_item_ids:
        ledger = repo.get_hunger_ledger(task_id)

snapshot = self.hunger_engine.tick(policy, clock, ledger, ...)
```

Behavior:

- If tier 0 is done, budget remains, and a next tier can be generated,
  the orchestrator saves those new items and continues.
- If tier 0 is done and loop budget is exhausted, it emits
  `BUDGET_EXHAUSTED`.
- If all configured tiers are done before budget exhaustion, it emits
  `DONE`.
- If tier 0 is not done and loop budget is exhausted, existing
  `HUNGER_EXPIRED` behavior remains.

This requirement avoids changing `HungerLedger.is_done()` into a
policy-aware method. The budgeted behavior belongs in orchestration,
where the policy, clock, ledger, and compiler are all available.

### 3.7 Planner must be tier-aware

**LM4-FR-7.** `RuleBasedPlanner` shall prefer the lowest unfinished
enabled tier before applying the existing `priority * gap_score` sort.

Ordering:

1. Lowest `refinement_tier` with active items.
2. Highest `priority * gap_score` inside that tier.

The worker mission shall include the tier:

```text
[phase=exploit tier=1 kind=tests] Make progress on H-REF-001...
```

This keeps correctness from competing with polish and makes traces
easier to audit.

### 3.8 Stagnation is configurable in budgeted mode

**LM4-FR-8.** `StagnationDetector` shall keep its default behavior.

When `policy.completion_mode == SPEND_BUDGET` and
`policy.respect_stagnation == False`:

- Per-item consecutive failure counts may still be recorded.
- Items shall not be auto-marked BLOCKED solely from consecutive
  failures.
- Global no-progress streak shall not emit `StopReason.BLOCKED`.
- The stop report shall include a recommendation noting that
  stagnation was ignored by policy.

This option is intentionally explicit. A budgeted run should not
silently disable stagnation.

### 3.9 CLI exposes real budget controls

**LM4-FR-9.** `hungerloop run` shall distinguish safety caps from
work budgets.

Existing:

```text
--max-loops N
```

remains a defensive cap for runaway orchestrator bugs.

New flags:

```text
--budget-loops N
--spend-budget
--refinement-profile NAME
--max-refinement-tier N
--ignore-stagnation
```

Effects:

- `--budget-loops N` sets loop-count decay budget for this run.
- `--spend-budget` sets `policy.completion_mode = SPEND_BUDGET`.
- `--refinement-profile NAME` sets `policy.refinement_profile`.
- `--max-refinement-tier N` sets `policy.max_refinement_tier`.
- `--ignore-stagnation` sets `policy.respect_stagnation = False`.

Validation:

- `--spend-budget` requires `--budget-loops`.
- `--spend-budget` with `--max-refinement-tier 0` is invalid unless a
  future flag explicitly means "burn budget on base retries only".
- `--ignore-stagnation` requires `--spend-budget`.
- `--max-loops` must be greater than or equal to `--budget-loops`
  unless the user explicitly wants a smaller defensive cap.

### 3.10 Context still carries recent loop evidence

**LM4-FR-10.** v0.5f.4 depends on the v0.5f prior-loop context path.

The budgeted refinement loop shall not introduce a second history
renderer. Refinement missions must flow through the same
`ContextBuilder -> ContextPack -> ExecutionWorker._messages` path.

Minimum prompt requirement for refinement loops:

- last worker summary
- recent failed checks
- recent successful committed tool evidence
- best workspace file inventory
- truncation audit when history is evicted

If a run produces two consecutive read-only rejected loops in budgeted
mode, the next prompt must include an explicit "act or declare blocker"
hint. This is a cross-loop mitigation, not a replacement for a future
intra-loop ReAct worker.

### 3.11 Events and reports

**LM4-FR-11.** The system shall add audit events:

```python
REFINEMENT_TIER_STARTED
REFINEMENT_ITEMS_ADDED
REFINEMENT_BUDGET_EXHAUSTED
```

Payload requirements:

- tier
- profile name
- added item ids when applicable
- previous accepted check keys count
- loop budget remaining

`StopReport.recommended_next_actions` shall include refinement-aware
recommendations for:

- budget exhausted with unfinished refinement items
- all configured tiers complete
- stagnation ignored
- no profile commands available

### 3.12 Preserve check-level commit invariant

**LM4-FR-12.** `CommitManager` shall not be relaxed.

A refinement loop commits only if:

- `newly_passed_check_keys` is non-empty,
- no previously passed check regressed,
- evidence is present.

Score-based commits remain forbidden. Refinement progress is still
check-level progress.

## 4. Non-Functional Requirements

**LM4-NFR-1.** Default mode backward compatibility is mandatory.
Existing tests that expect early DONE shall not be rewritten to pass.

**LM4-NFR-2.** Refinement generation is deterministic and idempotent.
Running `RefinementCompiler.ensure_next_tier()` twice against unchanged
state shall add no duplicate items.

**LM4-NFR-3.** No LLM calls are allowed in `RefinementCompiler`.

**LM4-NFR-4.** No broad validation. `ValidationGate` keeps targeted
validation plus previously passed regression checks.

**LM4-NFR-5.** `mypy --strict src/`, `ruff check src/ tests/`, and
`pytest tests/` must pass.

**LM4-NFR-6.** Budgeted refinement mode must not mask safety stops.
Hard cost/token ceilings and human pause/required paths keep priority.

## 5. Acceptance Criteria

### 5.1 Default DONE remains unchanged

Given a one-check task and default policy,
when the worker passes the check,
then the run stops with `StopReason.DONE`
and no refinement items are added.

### 5.2 Budgeted mode creates next-tier work

Given a one-check tier-0 task,
and `completion_mode=SPEND_BUDGET`,
and `max_refinement_tier=1`,
and `refinement_profile=python_medium`,
when tier 0 passes and loop budget remains,
then the orchestrator adds tier-1 hunger items
and continues instead of emitting DONE.

### 5.3 Empty ledger does not become BLOCKED in budgeted mode

Given all tier-0 items are satisfied,
and no active items remain,
and budgeted refinement mode can generate tier-1 work,
when the orchestrator steps,
then it does not call the empty-plan BLOCKED path.

### 5.4 Loop budget exhaustion after tier 0 is normal

Given tier 0 is satisfied,
and budgeted refinement mode is enabled,
and the loop budget is exhausted,
when the orchestrator steps,
then it emits `StopReason.BUDGET_EXHAUSTED`
and the stop report maps to `goal_status="completed"`.

### 5.5 Loop budget exhaustion before tier 0 remains hunger expired

Given tier 0 is not satisfied,
and the loop budget is exhausted,
when the orchestrator steps,
then it emits `StopReason.HUNGER_EXPIRED`
with the existing partial/abandoned mapping.

### 5.6 All configured tiers can still reach DONE

Given budgeted refinement mode is enabled,
and all tiers from 0 through `max_refinement_tier` are satisfied
before loop budget exhaustion,
when the orchestrator steps,
then it emits `StopReason.DONE`.

### 5.7 Stagnation policy is explicit

Given budgeted refinement mode with `respect_stagnation=True`,
when global no-progress reaches the threshold,
then the run emits `StopReason.BLOCKED`.

Given the same task with `respect_stagnation=False`,
when global no-progress reaches the threshold,
then the run continues until budget exhaustion or another terminal
condition.

### 5.8 CLI semantics are pinned

Tests shall prove:

- `--max-loops` alone does not enable budgeted refinement.
- `--budget-loops 10 --spend-budget --refinement-profile python_medium`
  updates `HungerPolicy` and runs in spend-budget mode.
- `--spend-budget` without `--budget-loops` fails with a usage error.
- `--ignore-stagnation` without `--spend-budget` fails with a usage
  error.

### 5.9 Refinement commits obey I-3

Given a refinement loop that writes files but passes no new check,
then `CommitManager` rejects it.

Given a refinement loop that passes a new tier-1 check with evidence
and no regressions,
then `CommitManager` promotes it.

### 5.10 Cross-loop anti-read-only hint

Given two consecutive rejected budgeted-refinement loops whose only
successful tool actions are `read_file`,
when the next worker prompt is built,
then the prior-loop context includes an explicit instruction to act
with a write/patch command or declare a blocker.

## 7. Open Questions

1. Should v0.5f.4 add soft cost/token budgets, or keep cost/token as
   hard `SAFETY_STOP` ceilings until a later release?
2. Should `python_medium` live in YAML task config only, or also be
   exposed as a built-in profile with default commands?
3. Should `BUDGET_EXHAUSTED` be allowed in default mode, or reserved
   strictly for `SPEND_BUDGET`?
4. Should the follow-on ReAct worker be v0.5g or v0.6?

## 8. Current Implementation Gap Summary

The implementation currently has:

- loop-count, token, and cost budget primitives,
- loop counter accounting,
- check-level commit gating,
- targeted validation,
- prior-loop context after v0.5f.

It still lacks:

- an explicit budget-spending completion mode,
- a normal budget-exhausted terminal reason,
- tier metadata on hunger items,
- a deterministic refinement item generator,
- orchestrator logic to create new work before DONE,
- tier-aware planning,
- CLI flags that set work budget rather than only safety caps,
- configurable stagnation behavior for budgeted runs,
- an anti-read-only prompt guard,
- integration tests proving budgeted incremental improvement.
