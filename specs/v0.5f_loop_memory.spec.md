# v0.5f — Cross-Loop Context Propagation

**Release:** v0.5f (proposed; first PRD section that touches the
three forward-compat hooks declared in v0.4.1 §18 and never spec'd
since)
**PRD:** **gap to be filled** — append a new section to
`hungerloop_v0_5d_e_prd_revised.md` titled
"§24. Cross-Loop Context Propagation"; this spec is the
implementation-side counterpart.
**Depends on:** v0.5e.1 shipped + commit `0568404` (goal-pass fix)
**Status:** spec → ready to implement (rev-3.1 after committed-loop semantic review)

---

## 1. Overview

### 1.1 What

Wire the three `ContextPack` hooks declared in v0.4.1 §18 — and
left dormant through v0.5.2 / v0.5b/c / v0.5d/e — into a real
data flow that lives **entirely inside `ContextBuilder`**. The
`ExecutionWorker` stays a pure consumer of pre-rendered text and
never acquires a repo / workspace handle.

```
WorkerResult.summary (last loop,        ─┐
   same agent_id only)                  ─┤
evidence rows (successful tool_call,    ─┼──►  ContextBuilder
   recent K loops, COMMITTED loops only)─┤      (reads via
LoopTrace + ValidationReport            ─┤       repo + injected
   (rejected, recent K loops)           ─┤       WorkspaceReader)
WorkspaceReader.list_files(best)        ─┘        │
                                                  ▼
                                          ContextPack populated:
                                            best_state_summary             ✓ (FR-7)
                                            best_workspace_files     NEW   ✓ (FR-7)
                                            last_self_summary        NEW   ✓ (FR-2,FR-5)
                                            failure_patterns_to_avoid      ✓ (FR-4)
                                            relevant_evidence_ids          ✓ (FR-3, audit)
                                            relevant_evidence_summaries  NEW ✓ (FR-3, prompt)
                                            truncation_info          NEW   ✓ (FR-10)
                                                  │
                                                  ▼
                                          ExecutionWorker._messages
                                            renders pre-built strings
                                            from ContextPack only
                                            (no repo, no I/O).
```

### 1.2 Why

Real-LLM testing on v0.5e.1 + `0568404` (goal-pass fix) showed:

- **`0568404` fixed the trivial loss-of-goal failure** (flagship-1
  fizzbuzz: BLOCKED-in-4 → DONE-in-2 once the user goal text and
  AcceptanceCheck params reach the model).
- **A second, deeper failure remains uncovered**: across loops the
  model sees the same prompt twice and repeats the same actions.
  In `flagship-1` Loop 1 ran `ls -la`; Loop 3 ran the same
  `ls -la` because Loop 1's existence had not been signalled
  anywhere in the Loop 3 prompt.

Goal-pass is a one-loop fix. v0.5f is the cross-loop fix. They're
orthogonal: `0568404` ensures the model knows **what** to build;
v0.5f ensures it knows **what's already been tried**.

### 1.3 User value

- Real "loop" semantics: the harness's name advertises iteration;
  today every loop is a fresh stateless attempt.
- Tighter token budget under failure: when a loop rejects, the
  next loop's prompt has the failure context inline, so the model
  converges faster instead of re-exploring.
- Foundation for v0.5d LearningWorker / v0.6 LLMPlanner: any
  worker beyond `execution_worker_v1` that wants to "learn from
  past loops" needs this same data flow. Building it once at
  `ContextBuilder` keeps every future worker on the same rail.

### 1.4 Non-goals

- **Multi-worker shared context**: scope here is one worker
  remembering its own past loops. Cross-worker memory in a single
  loop is v0.6 work.
- **Vector retrieval / similarity search**: history is supplied
  by recency only (last K loops). Semantic retrieval is v0.7+.
- **PromotedMemory injection**: cross-task memory recall is
  separate; that's v0.6 per PRD §17 plans. This spec only covers
  *within-task across-loop* context.
- **Plan / claim subsystem**: `relevant_claim_ids` stays unwired
  here. Claims are not a v0.5 concept; the field remains a
  forward-compat hook for v0.7+.
- **Compression / summarization via LLM**: all rendering is
  deterministic; no second model call to "summarize" a loop.
  Pure string concatenation with bounded length.

## 2. Layer responsibilities (read this first)

This spec (rev-3.1) assigns one owner per concern. **No layer
crosses this boundary.**

| Concern | Owner | Why |
| -- | -- | -- |
| Read prior `WorkerResult.summary` | `RepositoryProtocol.get_last_worker_result(...)` (NEW) | The summary is a structured field on `WorkerResult`, persisted via `save_worker_result`. The lookup is scoped by `agent_id` so one worker never inherits another worker's self-summary. |
| Read prior `LoopTrace` + `ValidationReport` | Existing repo APIs | Already exposed. |
| Read successful tool evidence | Existing repo APIs | `list_successful_tool_call_evidence(task_id)` already returns evidence id, loop id, and payload. Builder filters the returned rows by loop window. |
| **Render** evidence summaries | `ContextBuilder` | Worker has no repo. Renderer co-located with Builder so token-cap math sees final strings. |
| List workspace files | `WorkspaceReader` (NEW Protocol) implemented by `WorkspaceManager` | Repository has no `workspace_root`; `WorkspaceManager` owns the layout. Builder takes a `WorkspaceReader` via DI. |
| Cap total prompt history length | `ContextBuilder` | Owns final strings → can do exact char accounting. |
| Emit `context_truncated` audit event | `LoopOrchestrator` (NEW behavior) | Builder is on the read path; side-effects belong to the orchestrator, which already brackets `WORKER_STARTED`. Builder returns `ContextPack.truncation_info` describing what was truncated; orchestrator emits the event before `WORKER_STARTED`. |
| Render final user message | `ExecutionWorker._messages` | Pure function over `ContextPack`. No I/O. |

This layering removes all four high-severity findings:

- **#1**: Worker no longer dereferences IDs.
  `relevant_evidence_summaries: list[str]` is built in Builder.
- **#2**: `last_self_summary` source is `WorkerResult.summary`
  (structured), not the `response_preview` blob.
- **#3**: File listing moves to `WorkspaceReader` (Protocol owned
  by `WorkspaceManager`).
- **#4**: All rendered text exists in `ContextPack` before any
  cap is applied; per-section caps + total cap both enforced
  inside Builder.

## 3. Functional requirements (EARS)

### 3.1 ContextPack: additive fields

**FR-1.** The system shall extend `ContextPack` with these
**additive** fields (existing call sites need no update — Pydantic
defaults are safe):

```python
class ContextPack(BaseModel):
    # ... existing v0.4.1+v0.5.2 fields unchanged ...

    last_self_summary: str | None = None                      # NEW
    relevant_evidence_summaries: list[str] = Field(           # NEW
        default_factory=list
    )
    best_workspace_files: list[str] = Field(default_factory=list)  # NEW
    truncation_info: TruncationInfo | None = None             # NEW
```

with:

```python
class TruncationInfo(BaseModel):
    chars_before: int
    chars_after: int
    dropped_failures: int        # how many failure-pattern lines evicted
    dropped_evidence: int        # how many evidence summary lines evicted
    truncated_best_summary: bool # was BestState.summary clipped?
```

The three v0.4.1 forward-compat fields
(`relevant_claim_ids`, `relevant_evidence_ids`,
`failure_patterns_to_avoid`) keep their existing schema. Only
their **population logic** changes inside `ContextBuilder`.

`relevant_evidence_ids` retains its **audit-only** semantics: IDs
flow into the field for trace export and downstream tools, but
the prompt rendering uses `relevant_evidence_summaries` instead.

### 3.2 RepositoryProtocol: minimal read additions

**FR-2.** `RepositoryProtocol` shall add **one** new method:

```python
def get_last_worker_result(
    self,
    task_id: str,
    agent_id: str,
    before_loop_id: int,
) -> WorkerResult | None: ...
```

Returns the most recent `WorkerResult` whose `task_id` and
`agent_id` match and whose `loop_id < before_loop_id`, or `None`
if there is none. Both `InMemoryRepository` and `SQLiteRepository`
implement; the SQLite version is a single
`SELECT … WHERE task_id = ? AND agent_id = ? AND loop_id < ?
ORDER BY loop_id DESC LIMIT 1` against `worker_results`.

This is the only repo addition. All other reads use existing
APIs:

- `list_loop_traces(task_id)` to find prior rejected loops and
  their `validation_report_id`.
- `get_validation_report(validation_report_id)` to read failed
  `CheckResult` rows.
- `list_successful_tool_call_evidence(task_id)` to read successful
  tool-call evidence, then filter by loop window.
- `is_successful_evidence_payload(...)` remains the canonical
  success classifier, though the v0.5f prompt history only includes
  successful `tool_call` rows.

### 3.3 WorkspaceReader: a new Protocol

**FR-3.** Add `hungerloop.services.workspace_reader`:

```python
class WorkspaceReader(Protocol):
    def list_workspace_files(
        self,
        task_id: str,
        *,
        ref: Literal["best"] | Literal["candidate"],
        loop_id: int | None = None,
    ) -> list[str]: ...
```

Contract:

- `ref="best"`: list files under
  `{workspace_root}/tasks/{task_id}/best/files/`.
- `ref="candidate"`: requires `loop_id`. Lists files under
  `{workspace_root}/tasks/{task_id}/candidates/loop_{loop_id:03d}/files/`.
  Calling with `ref="candidate"` and `loop_id=None` raises
  `ValueError`.
- Returns paths **relative to the `files/` root**, sorted
  lexicographically, files only. Excludes:
  - any path component starting with `.` (e.g. `.pytest_cache`)
  - directories named `__pycache__`
- Reading a missing workspace returns `[]`, not an exception.

`WorkspaceManager` shall implement `WorkspaceReader`. Tests inject
fakes; v0.5f does not require expanding `WorkspaceManager`'s
public surface beyond conformance to the new Protocol.

### 3.4 ContextBuilder: dependency injection

**FR-4.** `ContextBuilder.__init__` shall accept a
`WorkspaceReader` parameter:

```python
class ContextBuilder:
    def __init__(
        self,
        repo: RepositoryProtocol,
        workspace_reader: WorkspaceReader,    # NEW
    ) -> None:
        self.repo = repo
        self.workspace_reader = workspace_reader
```

`orchestrator_factory` wires the production `WorkspaceManager` in
when constructing `ContextBuilder`. Existing tests that
construct `ContextBuilder` need to pass a `WorkspaceReader` —
ship a `tests/conftest.py` fixture `fake_workspace_reader` that
returns canned file lists.

### 3.5 Loop history loader

**FR-5.** `ContextBuilder` shall add a private helper:

```python
@dataclass(frozen=True)
class _LoopHistorySlice:
    rejected_lines: list[str]          # already rendered, FR-6
    successful_evidence_ids: list[str] # for FR-1 audit
    successful_evidence_lines: list[str] # already rendered, FR-6
    last_self_summary: str | None       # from WorkerResult.summary

def _loop_history(
    self,
    task_id: str,
    agent_id: str,
    current_loop_id: int,
) -> _LoopHistorySlice
```

Body:

1. **`last_self_summary`** ← `repo.get_last_worker_result(task_id,
   agent_id, current_loop_id).summary`. If the WorkerResult is
   missing or `summary == ""`, set to `None`.
2. **Rejected loops**: for each `LoopTrace` with
   `committed=False` AND `loop_id < current_loop_id` (most-recent
   first, capped at `K_REJECT_WINDOW`):
   - Pull its `ValidationReport`. For each
     `check_results[*]` with `passed=False`, format:
     `"loop {loop_id}: {check_key} {check_type} → {detail[:120]}"`
   - **Cap each line at `MAX_LINE_CHARS` = 200 chars** (clip with
     `…` suffix).
3. **Successful evidence**: load the set of **committed** loop ids
   first via `repo.list_loop_traces(task_id)` →
   `committed_loop_ids = {trace.loop_id for trace in traces if trace.committed}`.
   Then call `repo.list_successful_tool_call_evidence(task_id)`
   and keep rows that satisfy ALL of:
   - `evidence_type == EvidenceType.TOOL_CALL`,
   - `is_successful_evidence_payload()` returns True (defensive
     guard against future evidence-shape changes),
   - `loop_id in committed_loop_ids` (the row's loop actually
     promoted to `best/`),
   - `loop_id in range(current_loop_id - K_EVIDENCE_WINDOW,
     current_loop_id)`.

   Do NOT include `model_call` (model output is already covered by
   `last_self_summary`) and do NOT include `sandbox_run` (a
   `run_shell` action already has a successful `tool_call`
   envelope; including the paired sandbox row would double-count
   the action).

   The committed-only gate is the v0.5f semantic that distinguishes
   **"action that contributed to progress"** from **"tool call
   that did not crash"**. Without it, ls/find calls inside a loop
   that ultimately rejected would land in `relevant_evidence_summaries`
   under the prompt label "successful actions already on record",
   which actively *encourages* the same dead-end exploration the
   spec is trying to suppress (see Issue 1 in the rev-3.1 review).

   - Render each as
     `"loop {loop_id} {evidence_type} {tool_name}: {result_summary[:80]}"`.
   - Clip per-line at `MAX_LINE_CHARS`.
   - Sort deterministically as `loop_id DESC`, then by the row's
     original repository order ASC. The existing
     `list_successful_tool_call_evidence` contract is chronological
     order (`rowid ASC` on SQLite, insertion order in InMemory), so
     a Python stable sort by `-loop_id` preserves that as the
     in-loop tie-breaker.

**Window constants** (module-level in `context_builder.py`):

```python
K_REJECT_WINDOW = 3
K_EVIDENCE_WINDOW = 2
MAX_LINE_CHARS = 200
MAX_BEST_SUMMARY_CHARS = 800
MAX_LAST_SELF_SUMMARY_CHARS = 200
MAX_WORKSPACE_FILE_PATH_CHARS = 120
MAX_WORKSPACE_FILES_LINE_CHARS = 800
MAX_HISTORY_CHARS = 2000  # overall block budget AFTER per-section caps
```

### 3.6 Population

**FR-6.** `ContextBuilder.build_for_agent` shall populate:

- `best_state_summary` ← original `BestState.summary`, **clipped
  at `MAX_BEST_SUMMARY_CHARS`** with `…` suffix on overflow. Set
  `truncation_info.truncated_best_summary = True` when clipped.
- `best_workspace_files` ← `workspace_reader.list_workspace_files(
  task_id, ref="best")`, which returns sorted raw relative paths.
  Builder then converts it to a prompt-safe inventory:
  - Clip each path at `MAX_WORKSPACE_FILE_PATH_CHARS` with `…`
    suffix on overflow.
  - Start from the first 20 paths. If more raw paths exist, append
    the literal sentinel `"… (+{N} more)"` as the final element.
  - Compute the rendered line `files in best/: {joined}`. If that
    line exceeds `MAX_WORKSPACE_FILES_LINE_CHARS`, drop oldest
    rendered paths from the tail until it fits, folding every dropped
    path into the sentinel count. This keeps the inventory useful
    without allowing long path names to violate `MAX_HISTORY_CHARS`.
  The render step (FR-9) formats the final list as a comma-joined
  line.
- `last_self_summary` ← `_loop_history(...).last_self_summary`,
  clipped at `MAX_LAST_SELF_SUMMARY_CHARS`.
- `relevant_evidence_ids` ← `_loop_history(...)
  .successful_evidence_ids`. Order: `loop_id DESC`, repository
  order ASC within the same loop. Length cap =
  `K_EVIDENCE_WINDOW * 5 = 10`.
- `relevant_evidence_summaries` ← `_loop_history(...)
  .successful_evidence_lines`. Same order, same length cap.
- `failure_patterns_to_avoid` ← `_loop_history(...)
  .rejected_lines`. Order: most-recent first. Length cap =
  `K_REJECT_WINDOW * 4 = 12` (allowing multi-failed-checks per
  loop).

### 3.7 Total-block cap (FR-10 of rev-1)

**FR-7.** `ContextBuilder.build_for_agent` shall, after FR-6,
compute the **assembled history block** as:

```text
{last_self_summary}\n
{best_state_summary}\n
{best_workspace_files joined}\n
{failure_patterns_to_avoid joined by \n}\n
{relevant_evidence_summaries joined by \n}
```

Total `len()` ≤ `MAX_HISTORY_CHARS`. If over budget, **evict in
this order** until under cap:

1. Drop oldest `relevant_evidence_summaries` entries (and the
   matching `relevant_evidence_ids` to keep the two arrays
   parallel). Increment `truncation_info.dropped_evidence`.
2. Drop oldest `failure_patterns_to_avoid` entries.
   Increment `truncation_info.dropped_failures`.

Per-section caps in FR-6 (`MAX_BEST_SUMMARY_CHARS`,
`MAX_LAST_SELF_SUMMARY_CHARS`, `MAX_WORKSPACE_FILES_LINE_CHARS`)
guarantee that **even with both zero-eviction sections, the block
fits** in `MAX_BEST_SUMMARY_CHARS + MAX_LAST_SELF_SUMMARY_CHARS +
MAX_WORKSPACE_FILES_LINE_CHARS + structural overhead <=
MAX_HISTORY_CHARS`. This makes the eviction loop bounded and
proves FR-7 always converges.

`truncation_info.chars_before` / `chars_after` reflect the
assembled-block sizes around the eviction loop. When no
truncation happens, `truncation_info` stays `None` (Pydantic
default).

### 3.8 Orchestrator emits the audit event

**FR-8.** `LoopOrchestrator` shall, when `ContextPack
.truncation_info is not None`, emit a `CONTEXT_TRUNCATED` event
**before** the existing `WORKER_STARTED` event for the same loop.

```python
EventType.CONTEXT_TRUNCATED = "context_truncated"  # additive

# orchestrator pseudocode (matches RepositoryProtocol.append_event:
#   append_event(event_type, payload, *, task_id=None, loop_id=None))
context = self.context_builder.build_for_agent(...)
if context.truncation_info is not None:
    self.repo.append_event(
        EventType.CONTEXT_TRUNCATED,
        context.truncation_info.model_dump(),  # positional: payload
        task_id=task_id,
        loop_id=loop_id,
    )
self.repo.append_event(
    EventType.WORKER_STARTED,
    {...},  # positional: payload
    task_id=task_id,
    loop_id=loop_id,
)
```

This keeps the read path side-effect-free; only the orchestrator
writes to the events log when it has decided to dispatch the
worker.

### 3.9 ExecutionWorker._messages renders pre-built strings only

**FR-9.** `ExecutionWorker._messages(context)` shall remain a
pure function over `ContextPack`. It shall NOT receive `repo`
or any I/O handle. The "Prior loop context" block is appended to
the user message **only** when at least one of the following is
non-trivial:

- `context.last_self_summary is not None`
- `context.failure_patterns_to_avoid` non-empty
- `context.best_workspace_files` non-empty. Loop 1 prompt parity
  applies only to a fresh task with empty best/ and no prior
  history; if best/ already contains files, rendering the inventory
  is intentional.
- `context.relevant_evidence_summaries` non-empty

When suppressed, the message body is byte-identical to the
post-`0568404` v0.5e.1 output for the same inputs (FR-10
golden test).

When rendered, the block format is:

```text
Prior loop context (loop {loop_id} of this task):
- last attempt summary: {last_self_summary or 'n/a'}
- best state: {best_state_summary or 'empty'}
- files in best/: {best_workspace_files joined ', '}      # omit line if empty
- patterns to avoid (do NOT repeat these actions; they did not move any check):
  - {failure_patterns_to_avoid[0]}
  - ...
- successful actions already on record (refer to these instead of re-running):
  - {relevant_evidence_summaries[0]}
  - ...

If a previous loop already created a file you need, prefer
patch_file over a fresh write_file.
If you already explored the workspace last loop, do NOT explore
again — act on the patterns-to-avoid above.
```

The block is appended **before** the existing "Required JSON
shape example" block in the user message.

### 3.10 No-regression contract

**FR-10.** When all four trigger conditions in FR-9 are absent
(e.g. `loop_id == 1` AND empty best AND no prior evidence), the
generated user message shall be **byte-identical** to the
post-`0568404` output for the same `(mission,
acceptance_criteria, allowed_tools)` inputs. Pin via golden
test (NFR-3 / §5.9).

**FR-11.** `DummyModelClient` integration tests shall continue to
pass without modification. The dummy client ignores prompt
content; populating new `ContextPack` fields cannot change its
scripted output. Existing tests:
`tests/integration/test_orchestrator_dummy_done.py`,
`test_recovery_full_chain.py`,
`test_orchestrator_event_order.py`,
`test_orchestrator_human_required.py`,
`test_orchestrator_hunger_expired.py`,
`test_orchestrator_safety_stop.py`.

### 3.11 Filter scope: only committed-loop tool_call evidence

**FR-12.** `relevant_evidence_ids` and
`relevant_evidence_summaries` shall include **only** evidence
rows that satisfy ALL of:

1. `evidence_type == EvidenceType.TOOL_CALL`.
2. `is_successful_evidence_payload(payload) is True` — the tool
   call did not crash.
3. The row's `loop_id` belongs to a committed `LoopTrace`
   (i.e. the loop's candidate was promoted to `best/`).

They shall NOT include:

- `model_call` rows. Rationale: the model's prior output is
  already carried by `last_self_summary` (cleaner channel; FR-2).
  Including it in the evidence block double-renders the same
  content.
- `sandbox_run` rows. Rationale: `run_shell` already produces a
  successful `tool_call` envelope plus a lower-level sandbox row;
  including both would double-count one action and make §5.2
  nondeterministic.
- **`tool_call` rows whose loop ultimately REJECTED.** Rationale:
  a tool call that didn't crash but whose loop never moved any
  acceptance check forward is *not* an "action to refer to" — it's
  a dead-end. Surfacing it in the prompt under the label
  "successful actions already on record" sends the wrong signal
  and reinforces exploration loops (the exact failure mode v0.5f
  is built to break).

The committed-only gate is enforced inside `_loop_history`
(§3.5 step 3); the public field semantics are documented here.

This makes acceptance §5.2 deterministic and §5.2b semantically
correct.

### 3.12 Performance contract

**FR-13.** `ContextBuilder.build_for_agent` shall complete in
under **150 ms median** for a task with 50 loops + 200 evidence
rows + 25 best/ files. The disk walk in `WorkspaceReader` shall
be the dominant cost; profile per NFR-2.

## 4. Non-functional requirements

**NFR-1.** Determinism. For the same `(repo state, on-disk
workspace)`, two back-to-back `ContextBuilder.build_for_agent`
calls produce byte-identical `ContextPack` JSON. Workspace walk
**reads all files, then sorts, then truncates** — not "first 200
in fs order" (rev-1 had this wrong; fs traversal order is not
stable across kernels / filesystems).

**NFR-2.** Performance. Two read amplifications to be aware of:

1. `WorkspaceReader.list_workspace_files` walks the entire `files/`
   subtree (no early exit) so lexicographic top-K is correct, then
   `sorted()` then `[:20]`. For typical workspaces (<200 files)
   this is sub-millisecond. If a real task ever exceeds 5000
   files, that's a separate optimization; for now the simple
   implementation meets FR-13.

2. `repo.list_successful_tool_call_evidence(task_id)` returns
   **all** successful `tool_call` rows ever emitted on the task,
   not just the recent window. v0.5f calls this once per loop and
   discards rows outside `K_EVIDENCE_WINDOW`. For tasks at the
   FR-13 reference scale (≤ 50 loops, ≤ 200 evidence rows),
   the per-loop overhead is sub-millisecond — fine.

   **Scale ceiling**: when `task_loop_count > 200` AND average
   successful tool_calls per loop ≥ 3 (i.e. cumulative
   successful evidence > ~600 rows), v0.5f's "fetch all then
   filter in Python" pattern becomes the dominant cost on prompt
   builds. v0.5f does NOT optimize this. If a downstream worker
   (LearningWorker, ResearchWorker) routinely hits that scale,
   v0.5f.1 should add the windowed read addressed in Q6.

**NFR-3.** Golden test. Pin a fixture representing
"task with two prior failed loops + best/ containing two files"
into `tests/unit/test_context_builder_history.py`. The expected
text is committed verbatim. Any prompt drift requires updating
the golden — easy to spot in review.

**NFR-4.** Privacy. The rendered history shall NOT include:

- Full file *contents* of best/ files (only file *names* per
  FR-6 / FR-9).
- Full model-call response text. `last_self_summary` reads
  `WorkerResult.summary` (structured field, capped at
  `MAX_LAST_SELF_SUMMARY_CHARS = 200`), not `response_preview`.
- API keys, env vars, anything from `os.environ`.

**NFR-5.** Token cap (FR-7) is an INVARIANT, not a soft
recommendation. Per-section caps (`MAX_BEST_SUMMARY_CHARS`,
`MAX_LAST_SELF_SUMMARY_CHARS`, `MAX_LINE_CHARS` × line count) +
overall block cap together provide a closed-form bound:

```
total ≤ MAX_LAST_SELF_SUMMARY_CHARS              (200)
      + MAX_BEST_SUMMARY_CHARS                   (800)
      + files-in-best rendered line cap          (≤ 800)
      + (K_REJECT_WINDOW × 4 × MAX_LINE_CHARS)   (≤ 2400)
      + (K_EVIDENCE_WINDOW × 5 × MAX_LINE_CHARS) (≤ 2000)
      + structural overhead (\n, headers, …)     (≤ 200)
```

Worst case before eviction: ~6250 chars. After FR-7 eviction
loop, ≤ `MAX_HISTORY_CHARS = 2000`. Mathematically guaranteed.

**NFR-6.** Backward compat: schema-additive only. v0.5e.1 SQLite
databases work without migration. The four new
`ContextPack` fields (`last_self_summary`,
`relevant_evidence_summaries`, `best_workspace_files`,
`truncation_info`) are in-memory only — never persisted. The
three v0.4.1 list fields (`relevant_*`,
`failure_patterns_to_avoid`) are also in-memory; they're rebuilt
every loop.

**NFR-7.** Read-path purity. `ContextBuilder.build_for_agent`
shall NOT call `repo.append_event` or any other write API. The
audit event for truncation is emitted by `LoopOrchestrator` per
FR-8, not by the builder.

## 5. Acceptance criteria

### 5.1 Loop 1: empty history block suppressed


## 7. Open questions

- **Q1.** `last_self_summary` length cap (200 chars) is an
  educated guess. If real-LLM testing shows summaries are
  consistently truncated mid-thought, raise to 400 and re-pin
  the golden test.

- **Q2.** Should `failure_patterns_to_avoid` distinguish between
  "tool returned bad_args / failed" vs. "validation check stayed
  False" vs. "no tool was called at all"? Currently FR-5 lumps
  them via the validation report. Workers might want to know
  "my last write_file actually succeeded but didn't satisfy a
  check" vs. "my last tool call errored out". Defer to v0.5f.1
  if the distinction proves necessary.

- **Q3.** PRD §24 owner: who lands the PRD section — same author
  as this spec, or assigned via the v0.5f kickoff? Either is
  fine; the project convention has been "spec → impl" since
  v0.4.1, so the PRD must land before any code in this spec
  ships.

- **Q4.** `relevant_claim_ids` remains unwired. If a `Claim`
  type lands in v0.7 (per the original v0.4.1 §18 schema), the
  hook is ready. This spec does NOT remove the field; it just
  keeps it `[]`.

- **Q5.** Should `WorkspaceReader` also expose
  `read_file_summary(path)` (e.g. first 200 bytes) so future
  iterations can include peeked file content in
  `best_state_summary`? Out of scope for v0.5f (NFR-4 privacy)
  but the Protocol is the right place to evolve.

- **Q6.** Windowed read for `list_successful_tool_call_evidence`.
  Today the API returns the full task history; v0.5f calls it per
  loop and discards rows outside `K_EVIDENCE_WINDOW` (NFR-2). The
  proposed v0.5f.1 addition:

  ```python
  def list_successful_tool_call_evidence(
      self,
      task_id: str,
      *,
      since_loop_id: int | None = None,   # NEW; None = full history
  ) -> list[dict[str, object]]: ...
  ```

  Old callers (`SkillManager.derive_tools`) keep `since_loop_id=None`
  unchanged. The SQLite implementation gets a single
  `AND loop_id >= ?` clause; InMemoryRepository filters in Python.
  Defer until a worker actually exceeds the NFR-2 scale ceiling.

## 8. Why this should ship before v0.5d LearningWorker

The v0.5.2 §24 roadmap puts `LearningWorker` in v0.5d (and
`hungerloop_v0_5d_e_prd_revised.md` keeps it deferred).
`LearningWorker` by definition needs to *learn* across loops —
which requires this same `failure_patterns_to_avoid` /
`relevant_evidence_*` plumbing. If LearningWorker ships first,
it'll either:

- Build its own ad-hoc cross-loop reader, duplicating
  `ContextBuilder._loop_history` logic; **or**
- Ship without real cross-loop semantics (a "LearningWorker"
  that doesn't actually learn — same anti-pattern as the
  pre-v0.5e.1 SkillCard "shape exists, behavior empty").

Both outcomes are net-negative. v0.5f as a small focused release
that lands the `ContextBuilder` data flow once gives every
future worker (LearningWorker, ResearchWorker, the v0.6
LLMPlanner-driven workers) the same rail.

## 9. Out-of-scope reminders

- **Multi-worker shared context** (one worker reading another
  worker's evidence in the same loop) — v0.6.
- **Cross-task memory recall** (PromotedMemory injection into a
  new task's first loop) — v0.6 per existing PRD plans.
- **Vector / embedding search over evidence** — v0.7+.
- **LLM summarization of loop history** — explicitly forbidden
  (NFR-4 privacy + cost). All rendering is deterministic regex
  + format string.
- **Persisted ContextPack** — explicitly NOT added; the new
  fields are in-memory rebuilds, ensuring schema-additive only
  (NFR-6).
